# 計測の運用ランブック

`docs/redesign/11-metrics.md` の運用手順。**何を見るかより先に、何を見ないかを固定する。**

---

## 0. 最初に読むこと: 見てはいけない指標

以下を**主要指標として追わない**。原則1（判定しない）・原則2（数えない）と矛盾し、
追い始めると設計が逆流する。

| 追わない指標 | 追うとどうなるか |
|---|---|
| 記録日数 / 連続記録日数（ストリーク） | 上げようとすると催促通知が生まれ、punishy な設計に戻る |
| DAU（日次アクティブ） | 原則5（毎日を要求しない）と矛盾。**WAU を見る** |
| セッション時間 | 長い＝良いではない。30秒で終わるのが正しい |
| 壁打ちの利用回数 | 依存の形成を意味する可能性がある |
| セーフティ `block` の発火率を**下げる方向** | 検知を弱めるインセンティブが生まれる |
| 通知の開封率を**上げる方向** | 通知を増やす／煽る方向のインセンティブ |

> ダッシュボードにこれらを置かない。誰かが「今週のストリーク率は？」と聞いたら、
> このページを見せて理由を説明すること。

## 1. 毎朝: セーフティ

**成長ダッシュボードより先に見る。** 順番を守ることがこの運用の本体。

```bash
docker exec -i kokorobalance_db_1 psql -U postgres -d kokorobalance \
  < backend/db/queries/metrics-guardrails.sql
```

| 見るもの | 閾値 | 悪化時のアクション |
|---|---|---|
| セーフティ偽陰性件数（抽出レビュー） | **1件でも** | 辞書を即日更新し、原因を分析（`safety-review-runbook.md`） |
| 未レビュー件数 | 滞留させない | 月次レビューの実施状況を確認 |
| 「的外れ」報告率 | 3%超 | 壁打ちのプロンプト・応答型の選択を見直す |
| 通知OFF率 | 20%超 | 通知の本数・文面を見直す |
| 当日の支えリストが `none` の割合 | 50%超 | 支えリストの内容が空虚。0件表示の設計を見直す |

## 2. 週次

### 2.1 数値

```bash
for f in north-star funnel retention; do
  docker exec -i kokorobalance_db_1 psql -U postgres -d kokorobalance \
    < backend/db/queries/metrics-$f.sql
done
```

| ビュー | 内容 |
|---|---|
| 北極星 | 支えられた率（目標60%）と**母数（ふりかえり実施率）を必ず併記** |
| ファネル | オンボ §3.1 / 揺れ予報 §3.2 の各ステップ |
| リテンション | コホート別・セグメント別（§4.3） |

**注意すべき閾値**

- オンボで**揺れイベント登録が40%を下回ったら**、コンセプトのリスク1（言語化の認知負荷）が
  現実化している。テンプレの見せ方を疑う
- **2件目のイベント登録率（§3.2 #7）がリピートの本質指標。** 1回使って終わりなら成立しない
- 30日継続率は**インストール日コホート**で、**アプリを開いたこと**で判定する（記録したことにしない）

### 2.2 定性（数値より優先度が低いわけではない）

| 手段 | 内容 |
|---|---|
| **ストアレビューの全読** | iOS / Android の全レビューを読み、不満をタグ付けして集計 |
| 「的外れ」報告の全読 | `backend/db/queries/safety-reported-messages.sql` |
| 解約時アンケート | 1問・スキップ可。集計は任意記述もあわせて読む |

> 競合（Awarefy・muute・Upmind）の致命的な不満（オウム返し、ネガティブ否定、課金前の情報不足、
> ダークパターン）は**すべてストアレビューに書かれている**。競合はこれを読んでいないか、
> 読んで直していない。**週次でレビューを全読することが、最もコストの低い競争優位。**

## 3. 月次

| ビュー | 内容 |
|---|---|
| 目的 | 柱の新規追加率（目標20%）、確かな柱への昇格率（40%）、承認経路の内訳 |
| 収益 | 年額比率（目標60%）、初回更新率（40%）、ARPU、返金率 |
| セーフティの抽出レビュー | 資格保持者への委託（`safety-review-runbook.md`） |
| ユーザーインタビュー | 揺れイベントを2件以上完了した人に 5名/月 |

返金・チャージバック率は Stripe / App Store Connect のダッシュボードで確認する（DBには入っていない）。
**1%を超えたら課金訴求にダークパターンがないかを疑う。**

## 4. 指標のラベル（ME-07）

**目標のない指標を最適化対象にしない。** 新しい指標を足すときは必ずどちらかを付ける。

| ラベル | 指標 |
|---|---|
| 目標あり | 北極星（60%）、30日継続（12%）、週次点検実施率（50%）、柱の新規追加率（20%）、年額比率（60%）、初回更新率（40%）、オンボの各ステップ |
| 観測のみ | 承認経路の内訳、`felt_shake - expected_shake`、解約理由、ARPU、推しの `place` 判定率、備え完了経由の柱追加 |

## 5. 算出方法の変更履歴（ME-06）

30日継続率の定義を変えると過去との比較が壊れる。**変更したらここに追記する。**

| 日付 | 指標 | 変更内容 |
|---|---|---|
| 2026-08-01 | 30日継続率 | 初版。インストール日コホート、`event_logs` に何らかのイベントがある（＝アプリを開いた）ことで判定。D28〜D35 の窓で見る |
| 2026-08-01 | 北極星 | 初版。`was_supported ∈ {yes, partly}` / 全ふりかえり。母数としてふりかえり実施率を併記 |

**業界データとの比較の注意**: E-17（30日継続率の中央値3.3%、ピアサポート型8.9%）は
Google Play のパネルデータであり測定手法が異なる。**厳密な比較はできない点を報告時に必ず明記する。**

## 6. 計測してよいデータの制約（ME-01〜ME-05）

コード側で強制済み。破ろうとすると `sanitizeEventProperties()` に弾かれる。

| ID | 制約 | 実装 |
|---|---|---|
| ME-01 | 自由記述の本文を含めない（`mood_note`、ふりかえりのメモ、壁打ちの本文） | `backend/src/analytics/event-properties.ts` の許可リスト |
| ME-02 | 柱のラベルを分析基盤に送らない（`kind` と ID のみ） | 同上。`name` / `label` / `categoryName` は明示的に拒否 |
| ME-03 | セーフティ関連のイベントは別経路 | `safety_events` テーブル。`event_logs` とは分離済み |
| ME-04 | 第三者の分析・広告SDKに送るデータを最小限に | **第三者SDKを使っていない。** 自前の `event_logs` のみ |
| ME-05 | 分析へのオプトアウトを選べる | `profiles.analytics_opt_out`。設定＞プライバシー。**セーフティの検知はオプトアウト不可** |

新しいイベントプロパティを足したくなったら、`ALLOWED_KEYS` に明示的に追加する。
**「とりあえず全部送っておく」ができない構造にしてある。**

## 7. 実験の制約（11 §8.2）

メンタルヘルス領域なので、A/Bテストには倫理的制約がある。

| 禁止 | 理由 |
|---|---|
| セーフティ機能のA/B（片方に検知を入れない） | 論外 |
| 相談窓口の表示有無のA/B | 同上 |
| 罪悪感・不安を煽るコピーのA/B | 短期の数値は上がりうるが原則1に違反 |
| 通知頻度を大幅に上げる群を作る | 実害が出る |

**許容される範囲**: コピーの文言（同等の温度のもの同士）、UIの配置、テンプレの見せ方、価格の提示順。
