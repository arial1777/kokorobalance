# セーフティ 偽陰性レビュー 運用手順

対応仕様: `docs/redesign/03-spec-safety.md §6`（受入基準 A-08）。

## 目的

クライシス検知（`SafetyService`）が本来 `caution`/`block` と判定すべきだった入力を `clear` として見逃していないかを、人手で定期的に確認する。見逃し（偽陰性）は目標値 **0件**。1件でも見つかったら辞書（`safety_rules`）を即日更新する。

## 頻度

**月次**（毎月1日を目安）。

## 対象

1. **抽出レビュー**（`backend/db/queries/safety-review-sample.sql`）: `verdict='clear'` と判定されたassistant応答からランダム100件（事後放棄シグナルのあるものを優先）
2. **報告レビュー**（`backend/db/queries/safety-reported-messages.sql`）: 「この返信は的外れ／つらかった」報告があったもの **全件**

対象ユーザーは `safety_review_opt_out = false` の人のみ（プライバシーポリシーで明示済み）。リアルタイム検知そのものはオプトアウトの対象外。

## 体制

- レビュー担当は**最低2名**。判定が割れたケースは記録し、辞書改善の材料にする。
- 閲覧するのは抽出されたセッションのみ。全ログ閲覧権限は付与しない。
- **臨床心理士・精神保健福祉士など資格保持者への月1回のレビュー委託を推奨**。内部だけで判定を確定しない。

## 手順

1. 上記2クエリを本番DBに対して実行し、結果をCSVでエクスポートする（クエリ実行環境自体を、担当者2名以外がアクセスできない場所に限定する）。
2. 各レビュー担当者が独立に、それぞれのメッセージに対して「本来 `caution`/`block` だったか」を判定する（`clear` / `caution` / `block` の3択）。
3. 2名の判定を突き合わせる。
   - 一致: その判定を記録する。
   - 不一致: 3人目（推奨: 資格保持者）が最終判断する。
4. 「本来 `caution`/`block` だった」と確定したものは**偽陰性**としてカウントする。
5. 偽陰性が1件でもあれば:
   - 該当する表現を分析し、`safety_rules` に新しいルール（`rule_id`, `category`, `verdict`, `pattern`）を**即日**追加する。
   - 追加は本番DBへの直接`INSERT`で反映可能（デプロイ不要、`SafetyService` はTTL5分でキャッシュを再読込する）。
   - 追加したルールを `backend/db/migrations/` にも追記し、リポジトリと本番DBの内容を一致させる。
6. レビュー結果（件数・偽陰性件数・追加したルール）を記録に残す。

## プライバシー

- `SafetyEvent` に本文は保存されない（ハッシュのみ）。レビューは `ai_coach_messages.content`（既定90日保持）から直接行う。
- プライバシーポリシーに「安全性の確認のため、匿名化した会話をごく一部、人が確認する場合がある」旨とオプトアウト手段を明記する。
