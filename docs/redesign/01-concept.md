# 01. コンセプト再設計

> このドキュメントが再設計の中核です。以降の全機能仕様は、ここで定義した原則から導かれます。

---

## 1. なぜ変えるのか

現在のココロバランスは **「気分記録アプリ」** というカテゴリに属しています。このカテゴリは2026年時点で、次の4つが同時に成立している市場です。

1. **エビデンスが否定されている側**: 気分モニタリング介入のRCTメタ分析（2026年1月、8件）で、うつ症状への効果は **SMD −0.25〜−0.21（統計的に有意でない）**（E-16）
2. **継続率が最低水準**: メンタルヘルスアプリの30日継続率 中央値 **3.3%**。離脱者の39%が理由に「測定可能な改善がなかった」を挙げる（E-17, E-18）
3. **OSに無料で吸収済み**: 気分ログと睡眠・運動との相関表示は **Apple Health の State of Mind** として標準搭載（E-12）
4. **勝者が確定している**: Daylio 1,900万DL（2タップ記録）、Finch 1,250万DL・ARR $30M（E-19, E-20）

**このカテゴリで正面から戦う限り、勝ち筋はありません。** 一方で、現行アプリのコンセプト（支えを複数持つ）そのものは、**効果量が桁違いに大きい学術的根拠を隣に持ちながら、誰もプロダクト化していない領域**に接しています。

| 比較 | 効果量 |
|---|---|
| 気分モニタリング介入（現行アプリの位置） | SMD **0.08〜0.25**（有意でない） |
| 社会的グループ所属を増やす介入（Groups 4 Health, RCT） | **d 0.71〜1.07**（抑うつでCBTに非劣性） |

やることは**コンセプトの捨て替えではなく、実装している軸の付け替え**です。

## 2. 新コンセプト

### 2.1 カテゴリの定義

> **気分記録アプリ → 心の防災アプリ（メンタル・プリペアドネス）**

「今日の気分を記録して振り返る」のをやめ、**「揺れる日が来る前に備える」**に主機能を移します。

| | 旧 | 新 |
|---|---|---|
| 時間軸 | 過去（事後の可視化） | **未来（事前の準備）** |
| 頻度 | 毎日 | **週1回 ＋ 揺れる日の前後** |
| 主オブジェクト | 円グラフ（構成比） | **揺れイベントと、それに備える柱** |
| ユーザーの動機 | 「記録しなきゃ」 | **「あの日が来る」** |
| 開く理由 | 習慣（続かない） | **予定（自明）** |
| 成功の定義 | 記録日数 | **揺れた日を、支えられて越えられたか** |

### 2.2 一行のポジショニング

> **揺れる日に、備えておく。**

補助コピー案:

- 「推しの卒業発表の日。契約更新の日。あの日が来る前に、支えをもう1つ。」
- 「心の防災は、揺れてからでは間に合わない。」
- 「毎日開かなくていいアプリです。週に1回、それで足ります。」

### 2.3 プロダクトの一文定義（社内共有用）

> ココロバランスは、**心が揺れそうな日を事前に登録すると、その日までに支えを厚くする準備を一つずつ提案し、当日は「あなたには他にこれがある」という具体的なリストを差し出す**アプリです。揺れが過ぎたあとに「どの支えが効いたか」を回収し、次回の精度を上げます。

## 3. 設計原則（全機能に適用する憲法）

以降の仕様は、この6原則に違反してはいけません。レビュー時のチェックリストとして使ってください。

### 原則1: 判定しない (No Verdict)

**ユーザーの心の構成を「偏っている／足りない」と評価する表現・UIを置かない。**

self-monitoring は "oppressive"（抑圧的）"punishy"（罰的）と体験され、動機づけではなく罪悪感と恥を生みます（E-06）。競合 muute の実レビューには「『ネガティブ多い。来週は発見や喜びも報告してもらえると嬉しい』というインサイトが届いてがっかりした」があります（E-09）。

| 禁止 | 代替 |
|---|---|
| 「柱が0本です」 | （0本の状態を作らない。→ 原則4） |
| 「バランスが偏っています」 | 「いまは〈仕事〉が中心ですね」 |
| 「次に育てるといい柱」 | 「もし余力があれば、こんな手もあります」 |
| 「まだレポートがありません」 | 「あと1回の点検で、最初のふりかえりが出せます」 |
| 達成率・スコア・偏差の表示 | 表示しない |

### 原則2: 数えない (No Counting)

**連続記録日数（ストリーク）、達成率、柱の本数を主要指標として前面に出さない。**

ストリークは途切れた瞬間に離脱理由に変わります。柱の本数は、次の原則3を満たさない限り意味を持ちません。

- ストリーク機能は**新規実装せず、既存にあれば撤去**
- 柱の本数を表示する場合は「**確かな柱** N本」と「**育て中** M本」を分け、合計値を強調しない

### 原則3: 承認されていない支えを、支えとして数えない (Verification First)

identity accumulation 研究の決定的な条件です。**支えの累積が well-being を高めるのは、それが他者から承認（verified）されている場合のみ。承認されていない支えの累積は well-being を低下させます**（E-05）。

- 柱には `verified` 属性を持たせる（→ `07-spec-pillars.md`）
- 単独活動の柱（睡眠・投資・筋トレ）は原理的に承認されないため、**「柱」ではなく「習慣」として別扱い**にする
- 「相手からも、あなたの居場所として認識されている？」を問う設計を入れる

### 原則4: 空の状態を作らない (No Empty State)

現行アプリは初回訪問時に「柱 0本」「レポートなし」「グラフに実データなし」と、**3つの空状態を同時に見せています**。コールドスタートの死のループ（価値を得るには継続が必要／継続には価値が必要）はここで発生します。

- オンボーディング完了時点で、**必ず1本以上の柱と、1件以上の揺れイベント候補が存在する**状態を作る
- データが足りない画面は**表示しない**（タブ自体を出さない）。「まだありません」を見せるより出さないほうが良い
- 初回セッション内で、**ユーザーが「持って帰れるもの」を1つ渡す**（→ `05` の初回備えリスト）

### 原則5: 毎日を要求しない (Weekly by Design)

日本の未利用理由の第2位は「記録が面倒（28.8%）」（E-21）。日次記録の勝者はすでに確定しています。

- 定期接触は**週1回**。これをコピーで明示的に宣言する（「週1回だけ。それで十分です」）
- 週次以外の接触理由は**揺れイベントの日付が作る**（プロダクト側の都合ではなくユーザーの現実が呼ぶ）
- 毎日開くユーザーを止めはしないが、**毎日開かないことを失敗として扱わない**

### 原則6: 危機を検知したら、AIは黙る (Silence on Crisis)

LLM は自殺を示唆したユーザーに橋のリストを返した事例が査読論文に記録されています（E-10）。米国では4州が AI セラピーを完全禁止（E-15）。**AIの応答品質を上げる方向で解決してはいけません。遮断で解決します。**

- 決定的なシグナルを検知したら **AIの応答を生成せず**、相談窓口のみを提示する
- 偽陰性（見逃し）を測定可能にする（→ `03-spec-safety.md`）

| 系統 | トリガー | 頻度 | 通知手段 |

| 任意 | 壁打ち（AI） | 毎日1往復まで可 | なし（ユーザー起動） |

## 5. 柱の再定義

現行の24カテゴリのうち、他者を伴うのは4項目のみでした（C-02）。エビデンスがあるのは社会的つながりの側なので、**柱を3つの型に分けます**。

| 型 | 定義 | 例 | 承認 | 「柱」として数えるか |
|---|---|---|---|---|
| **居場所（Place）** | 継続的に所属し、他者から所属を認識されている集団 | 職場のチーム、サークル、推しのファンコミュニティ、家族、バンド、常連の店 | 可能 | **○（確かな柱）** |
| **関係（Relation）** | 特定の個人との関係 | 恋人、親友A、同僚B、きょうだい | 可能 | **○（確かな柱）** |
| **習慣（Habit）** | 単独で完結する活動 | 睡眠、筋トレ、投資、読書、ゲーム、1人時間 | 不可 | **×（「習慣」として別枠）** |

### 重要な設計判断: 「推し」は居場所になりうる

現行LPは「推しの卒業発表を見た日」を**脆さの象徴**として描いています。しかしデータは逆を示します。

- 20代女性の**45%**が推しを持つ。推し活支出は物価高でも**54.0%が「全く削らない」**（E-14）
- 第一生命経済研究所は、推し活が寄付と同様の**利他性に基づく満足感**でウェルビーイングに寄与すると指摘

**したがって「推しに依存しすぎ」というメッセージは、最もDLしそうな層への侮辱です。** 新設計では:

- 「推し」を **単独の消費**ではなく **居場所（ファンコミュニティ）** として登録できるようにする
- メッセージを反転する: ~~「推しだけでは危ない」~~ → **「卒業発表の日に備えておこう」**
- 推し活イベント（ライブ最終日、卒業、契約満了、活動休止）は、**揺れ予報の最も需要が明確なユースケース**として一級市民扱いする

## 6. 何を捨てるか

捨てる判断を明文化しておかないと、機能が足し算で残ります。

| 捨てるもの | 理由 | 移行先 |
|---|---|---|
| **毎日の記録** | 「面倒」が未利用理由2位。日次の勝者は確定済み | 週次点検（06） |
| **主画面の円グラフ** | Apple Health に無料で内蔵済み。かつ実データになるまで数週間かかる | ふりかえりタブの奥（06） |
| **柱の本数のカウント表示** | 原則2・3に違反 | 「確かな柱／育て中」の分離表示（07） |
| **「次に育てるといい柱」という宿題型の提案** | 原則1に違反 | 揺れイベントに紐づく「備え」（05） |
| **「AIコーチ」という名称** | 職能名＋行動指示は規制の方向と逆。期待値も上がりすぎる | 「壁打ち」（08） |
| **AI 月3回の回数制限** | 唯一の行動支援を週1未満に絞ると習慣化しない | 「毎日1往復・深さで課金」（08） |
| **「充足度ポイント」** | 定義が不明瞭で、原則2（数えない）に触れる | 撤去 |
| **PWAのみでの提供** | ストア検索という唯一の低CACチャネルを放棄している | ネイティブラッパー（04） |

## 7. 情報アーキテクチャ（新）

```
タブ（4→3に削減）
├── 今週          ← 主画面。週次点検 と 直近の揺れイベント だけ
├── 揺れ予報      ← イベント一覧・登録・備えの管理
└── ふりかえり    ← 週次サマリ／柱の一覧／円グラフ（この奥）

設定（タブ外）
└── 柱の管理 / 通知 / ペア / プラン / 相談窓口 / 規約
```

### 主画面「今週」の表示規則

**上から順に、条件を満たす最初のものだけを大きく出す**（複数を同時に並べない）。

| 優先 | 条件 | 表示 |
|---|---|---|
| 1 | 揺れイベントが D-3 〜 D+0 | **その日のための支えリスト**（→ 05） |
| 2 | 揺れイベントが D-14 〜 D-4 で未完了の備えがある | **今週の備え 1つ** |
| 3 | 揺れイベントが D+1 〜 D+7 で未ふりかえり | **ふりかえり（1タップ）** |
| 4 | 今週の点検が未完了 | **週次点検（30秒）** |
| 5 | 上記すべてなし | **「今週は穏やかそうです」＋ 揺れそうな予定の追加導線** |

優先5の状態を「何もない空画面」にしないことが原則4の適用です。

## 8. ターゲットの再定義

現行LPは「恋人・仕事・推し」と広く網を張っていますが、**揺れる日が事前にわかる人**に絞ると獲得効率が上がります。

### 一次ターゲット（獲得の入口）

| セグメント | 事前にわかる揺れ | 規模の根拠 |
|---|---|---|
| **推し活層** | 卒業・活動休止・ラストライブ・契約満了・移籍発表 | 20代女性45%が推しを持つ（E-14） |
| **社会人（転機）** | 異動発表、契約更新、査定面談、繁忙期、退職日、転職初日 | — |
| **受験・資格** | 合否発表日、試験日 | — |
| **関係の転機** | 引っ越し、卒業、遠距離化、結婚・離婚の手続き日 | — |

### 二次ターゲット（B2B、2028年に向けて）

50人未満事業場のストレスチェックが**2028年4月1日に義務化**されます（E-22）。日付が確定した購買トリガーです。詳細は `10-pricing-b2b.md`。

## 9. 訴求の根拠を差し替える {#evidence-swap}

**マーケティングコピーで引用する学術的根拠を、以下のとおり入れ替えます。**

| | 旧（使ってはいけない） | 新（使うべき） |
|---|---|---|
| 理論 | self-complexity 緩衝仮説（Linville 1987） | **Social Identity Approach**（Cruwys, Haslam ら） |
| 状態 | 再現失敗。メタ分析で緩衝効果への支持が「ほとんど見出されなかった」。逆方向の知見（低自己複雑性の利点）も存在 | 縦断コホート n=5,055・2年追跡 ＋ 非劣性RCT n=174 |
| 言えること | （言えない） | **「居場所を1つ増やすと、うつの再発リスクは24%下がる。3つで63%」**（既にうつのある人において） |
| 出典 | E-01, E-02 | E-03, E-04 |

> **注意**: 「支えを分散すればストレスに強くなる」という一般化されたポートフォリオ理論は、学術的に支持されていません。効いているのは「**主観的に重要で、かつ他者から承認された社会的グループへの帰属**」という具体的なメカニズムです。コピーを書くときは、抽象的な分散の話にせず、**居場所と関係の話**にしてください。

## 10. 名称について {#naming}

**未解決の意思決定事項です。**

「ココロバランス」は **一般社団法人ココロバランス研究所（kokorobalance.jp）** が使用中です。同法人はカスタマーハラスメント対応・こころのウェルビーイングを扱うB2B組織で、ドメインは `.jp` と `.app` の違いのみ。

| リスク | 内容 |
|---|---|
| SEO | 指名検索で勝てない。実際に「ココロバランス アプリ」で検索してもアプリは上位に出ず、同法人と別サービス（COCOLOLO）が占める |
| 商標 | 未評価。**法務確認が必要** |
| B2B展開時 | 同法人が同一領域のB2Bプレイヤーであるため、法人営業で混同が起きる |
| 類似 | COCOLOLO（心拍ゆらぎで気分を測るアプリ、150万DL）も名称・領域が近い |

### 判断の選択肢

1. **維持**: 商標調査でクリアなら維持。ただしSEOは指名検索を諦め、ストア内検索とイベント名キーワード（「推し 卒業 つらい」等）に投資
2. **改称**: 新コンセプト（心の防災）に合わせる。方向案は「揺れ」「備え」「防災」の語彙 — 例: `ユレヨホウ` / `ココロ防災` / `そなえ`
3. **サブブランド**: 「ココロバランス」を法人／サービス名として残し、主機能名を「揺れ予報」として前面に出す

**推奨: 3 →（商標に問題があれば）2。** コンセプトを変えるタイミングは改称の最良の機会でもありますが、既存ユーザーとSEO資産（ブログ記事）を捨てるコストがあるため、まず商標調査の結果を待ちます。

## 11. 成功の定義

原則1・2に従い、「記録日数」をKPIにしません。

| 階層 | 指標 | 目標 | 理由 |
|---|---|---|---|
| **北極星** | **揺れイベントを「支えられて越えた」と回答した率**（D+3 のふりかえりで） | 60%以上 | プロダクトの約束そのもの |
| 先行指標1 | オンボ完了者のうち、揺れイベントを1件以上登録した率 | 70%以上 | 主機能への到達 |
| 先行指標2 | 備え（PrepAction）の完了率 | 40%以上 | 行動支援が機能しているか |
| リテンション | **30日継続率** | **12%以上**（業界中央値 3.3%、トラッカー型 6.1%、ピアサポート型 8.9% の上を狙う） | E-17 |
| 収益 | 年額プラン比率 | 60%以上 | 年額の380日継続 19.9% > 月額 14.2%（E-13） |
| **セーフティ** | **クライシス検知の偽陰性件数** | **0を目標に、常時監視** | 03 |

詳細は `11-metrics.md`。

## 12. このコンセプトが失敗する条件（事前の反証）

正直に書いておきます。以下が起きたらコンセプトを疑うべきです。

1. **揺れイベントを登録してもらえない**: 「揺れそうな日」を自分で言語化することは、記録より認知負荷が高い可能性がある。→ 緩和策: オンボで**カテゴリ別のテンプレート**から選ばせる（「推しの卒業」「契約更新」等）。自由記述を要求しない。
2. **揺れイベントの頻度が低すぎる**: 年に2〜3回しか揺れる予定がない人には、アプリを開く理由が週次点検だけになる。→ 緩和策: 週次点検を単体で価値のあるものにする（06）。ただしこれは現行アプリの弱点に戻る道なので、注意が必要。
