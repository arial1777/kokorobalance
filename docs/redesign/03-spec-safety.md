# 03. セーフティ仕様（クライシス検知）

**優先度: P0（最優先）** / 対応課題: C-11, C-18

> このドキュメントの内容は「あったほうがいい機能」ではありません。**実装されていない状態で運用を続けることが、事業継続上の最大のリスク**です。

---

## 1. なぜ P0 なのか

| 事実 | 出典 |
|---|---|
| Stanford/CMU らの査読論文で、LLM は失職後に自殺を示唆したユーザーが「橋のリスト」を求めた際、**文脈を捉えず単に橋を列挙した**（7cups Noni、Character.ai therapist） | E-10 |
| 同研究: モデルは**妄想的思考を追認し、メンタルヘルスクライシスを認識できず、確立された治療実践に反する助言を与えた**。**より高性能な新しいLLMでもバイアスは同程度** | E-10 |
| APA（2025年11月）: 生成AIは**心理療法・診断・クライシス支援に使用すべきでない**。「承認的な応答は必ずしも正確ではなく、短期的な安堵は持続的な症状改善に転換しない」 | E-11 |
| FDA Digital Health Advisory Committee（2025年11月）が特定したリスクに**「悪化や自殺念慮の検知失敗」**が明記され、市販前エビデンスとして**「有害事象の偽陰性を透明に測定すること」**を推奨 | E-24 |
| Character.AI / Google は複数の10代自殺関連訴訟について**2026年1月に原則合意（settlement in principle）** | E-25 |
| **イリノイ・ネバダ・ロードアイランド・メインが AI セラピーを完全禁止**。2026年Q1だけで36州が70件超の法案を提出 | E-15 |

現行アプリには免責表記とよりそいホットラインの導線があり、これは競合より丁寧です。**しかし免責は検知の代わりになりません。**

## 2. 設計方針

### 2.1 基本方針: 検知したら、AIは黙る

原則6（`01-concept.md`）の実装です。**AIの応答品質を上げる方向で解決しません。遮断で解決します。**

理由: LLM のクライシス応答失敗は、モデルの性能向上で解決しないことが実証されています（E-10）。「もっと良いプロンプトを書く」は対策になりません。

### 2.2 三層判定

すべてのユーザー自由記述入力を、AIに渡す**前**に判定します。

| 判定 | 意味 | AIの応答 | 追加表示 | 記録 |
|---|---|---|---|---|
| `block` | 自殺念慮・自傷・他害・切迫した危機のシグナル | **生成しない** | 相談窓口カードのみ | `SafetyEvent(verdict=block)` |
| `caution` | つらさが強いが切迫の明示なし | 生成する（ただし制約付きプロンプト） | 応答の下に相談窓口を併記 | `SafetyEvent(verdict=caution)` |
| `clear` | 上記以外 | 通常生成 | なし（常設の免責のみ） | 記録しない |

### 2.3 検知の対象範囲

**壁打ち（AI）だけでは不十分です。** 自由記述が入る全箇所を対象にします。

| 対象 | 参照 | 判定タイミング |
|---|---|---|
| 壁打ちの入力 | `08` | 送信時（AI呼び出し前） |
| `WeeklyCheck.mood_note` | `06` | 保存時 |
| `ShakeReview.note` | `05` | 保存時 |
| `ShakeEvent.title` | `05` | 保存時 |
| `Pillar.label` | `07` | 保存時（低優先だが対象に含める） |

壁打ち以外の箇所では AI の応答が存在しないため、`block` 時の挙動は「**保存はする。保存完了画面に相談窓口カードを出す**」とします。**入力を拒否して保存させないのは誤りです**（書けた事実を否定することになる）。

## 3. 検知ロジック

### 3.1 二段構成

```
ユーザー入力
    │
    ▼
[第1段] 決定的ルール（辞書＋正規表現）      ← 高再現率を優先。誤検知を許容する
    │
    ├─ ヒット ────────────────────► block（AI呼び出しなし）
    │
    ▼ ヒットなし
[第2段] 分類器（LLM を「分類専用」で呼ぶ）  ← 生成ではなく分類。出力は enum のみ
    │
    ├─ block ─────────────────────► block
    ├─ caution ───────────────────► caution（制約付きで応答生成）
    └─ clear ─────────────────────► 通常応答
```

### 3.2 第1段: 決定的ルール

**設計思想: 偽陽性（過剰検知）を許容し、偽陰性（見逃し）を最小化する。**

「大げさに窓口を出してしまった」の損害は小さく、「見逃した」の損害は回復不能です。この非対称性を設計に反映します。

ルールカテゴリ（**実際の辞書は本ドキュメントに列挙しません**。理由は §3.3）:

| ルールID | カテゴリ | 判定 |
|---|---|---|
| `R-SI-*` | 自殺念慮の直接表現 | `block` |
| `R-SI-PLAN-*` | 手段・場所・時期への言及 | `block` |
| `R-SH-*` | 自傷行為 | `block` |
| `R-HARM-*` | 他害の意図 | `block` |
| `R-ABUSE-*` | 虐待・DV の被害示唆 | `block`（窓口は専用のものに差し替え → §5.2） |
| `R-ED-*` | 摂食障害の危険な行動 | `caution`（`block` にすると相談を封じるため） |
| `R-SUB-*` | 依存物質の危険な使用 | `caution` |
| `R-DISTRESS-*` | 強い絶望・無価値感（切迫の明示なし） | `caution` |

**実装要件**

- 表記ゆれに耐えること: ひらがな／カタカナ／漢字／ローマ字、伏せ字（「し○たい」）、記号挿入（「し・に・た・い」）、絵文字混在
- 否定文脈の考慮は**最小限に留める**。「死にたくない」を `clear` にする最適化は、誤って `clear` に落とすリスクがあるため、**迷ったら block**
- ルール辞書は**コードにハードコードせず、更新可能な設定として持つ**（誤検知報告を受けて即日更新できること）
- 各ルールに `rule_id` を振り、`SafetyEvent.matched_rules` に記録する（精度改善のため）

### 3.3 辞書を本ドキュメントに列挙しない理由

具体的な検知語のリストを設計文書に平文で置くと、**回避方法の一覧としても機能します**。辞書は実装リポジトリの限定アクセス下（または設定ストア）に置き、本書からは参照のみとしてください。

### 3.4 第2段: 分類器

- **生成ではなく分類として呼ぶ**。出力スキーマを `{verdict: "block"|"caution"|"clear", confidence: number}` に固定し、自由文を返させない
- 分類器がタイムアウト・エラーになった場合の**フォールバックは `caution`**（`clear` にフォールバックしてはいけない）
- 分類器のプロンプトには会話履歴を含める（単発の文では「橋のリスト」型の文脈依存リスクを捉えられない）
- **分類器の応答をユーザーに見せない**

### 3.5 レイテンシ要件

| 段 | 目標 | 上限 |
|---|---|---|
| 第1段 | 10ms 未満 | 50ms |
| 第2段 | 800ms | 2,000ms（超過時は `caution` でフォールバック） |

判定中の UI は「考えています…」で、**判定していることを明示しない**（監視されている感を与えない）。

## 4. `block` 時の挙動

### 4.1 表示するもの

AI の応答を**生成せず**、代わりに以下のカードのみを表示します。

```
┌────────────────────────────────────────────┐
│                                            │
│  いま、ひとりで抱えるにはしんどい話だと     │
│  思います。                                │
│                                            │
│  このアプリでは、ここから先はお話しできま   │
│  せん。かわりに、24時間つながる窓口をお伝   │
│  えします。                                │
│                                            │
│  ┌──────────────────────────────────────┐  │
│  │ よりそいホットライン                 │  │
│  │ 0120-279-338（24時間・通話無料）     │  │
│  │                        [電話をかける] │  │
│  └──────────────────────────────────────┘  │
│  ┌──────────────────────────────────────┐  │
│  │ いのちの電話（SNS相談も）            │  │
│  │                        [ひらく]       │  │
│  └──────────────────────────────────────┘  │
│                                            │
│  書いてくれた内容は保存されています。      │
│  消したいときは、ここから消せます。[削除]  │
│                                            │
└────────────────────────────────────────────┘
```

### 4.2 コピーの原則

| 原則 | 理由 |
|---|---|
| **「できません」の前に受け止めを置く** | 拒否から始めると突き放しになる |
| **AIのふりをして共感を続けない** | APA が警告する「承認的な応答による誤った安堵」（E-11） |
| **理由を「アプリの限界」として説明する** | 「あなたの話が重すぎる」ではなく「こちらの限界」にする |
| **電話番号はタップで発信できる** | 危機時に番号を書き写させない |
| **書いた内容を削除できる導線を同時に置く** | 「言ってしまった」後悔への配慮 |
| **ネガティブな絵文字・アイコンを使わない** | 警告色（赤）も使わない。落ち着いた配色 |

### 4.3 やってはいけないこと

- ❌ 入力の**送信を拒否する**（「この内容は送れません」）→ 検閲として体験される
- ❌ 通報・第三者への自動連絡（**法的根拠なく行わない**。同意なき第三者通知は別途の法務判断が必要）
- ❌ アカウントの一時停止・機能制限
- ❌ 「専門家に相談してください」だけで終わる（**具体的な窓口を出す**）
- ❌ 検知回数をユーザーに見せる

## 5. 相談窓口の管理

### 5.1 要件

- 窓口リストは**コードにハードコードせず、設定として管理**（番号・受付時間・URLは変わる）
- 各窓口に `available_hours` を持ち、**深夜なら24時間対応の窓口を上位に並べ替える**
- 電話が苦手なユーザー向けに**SNS/チャット相談**を必ず1つ含める（Z世代の主要チャネル）
- リンク切れ・番号変更の**月次チェックを運用タスクとして定義**する

### 5.2 検知カテゴリ別の窓口切り替え

| 検知カテゴリ | 提示する窓口 |
|---|---|
| `R-SI-*` `R-SH-*` `R-DISTRESS-*` | よりそいホットライン / いのちの電話 / こころの健康相談統一ダイヤル |
| `R-ABUSE-*`（DV・虐待） | **DV相談＋（プラス） / 児童相談所虐待対応ダイヤル 189** |
| `R-ED-*` | 摂食障害の相談窓口 |
| `R-SUB-*` | 依存症の相談拠点 |
| `R-HARM-*` | よりそいホットライン（＋警察相談専用 #9110 を併記） |

**カテゴリを取り違えた窓口を出すのは、出さないより悪い**（DVの相談者に自殺相談窓口を出すなど）。分類の粒度を最低限このレベルまで持つこと。

### 5.3 既存の `/support-resources` ページ

現行アプリには既に相談窓口ページがあります。**この資産を活かし、検知時のカードから遷移できるようにする**こと。ただしカード自体に電話番号を直接置く（1タップで発信できる）ことは必須です。

## 6. 偽陰性の測定 {#false-negative}

FDA 委員会が「**有害事象の偽陰性を透明に測定すること**」を推奨しています（E-24）。自主的に実装します。将来 B2B・自治体・大学に販売する際の資産にもなります。

### 6.1 測定方法

| 手段 | 内容 | 頻度 |
|---|---|---|
| **A. 抽出レビュー** | `verdict = clear` と判定された壁打ちセッションから**ランダムに月100件**を抽出し、人間が「本来 caution/block だったか」を判定 | 月次 |
| **B. 事後シグナル** | `clear` 判定の直後に**ユーザーが会話を放棄した**セッション（応答後に離脱し、7日以上再訪なし）を優先的にレビュー対象に含める | 月次 |
| **C. ユーザー報告** | 「この返信は的外れ／つらかった」の1タップ報告ボタンを全AI応答に付ける。報告されたものは全件レビュー | 常時 |
| **D. レッドチーム** | 表記ゆれ・伏せ字・遠回しな表現・多言語混在を含むテストケースを維持し、リリースごとに実行 | リリース毎 |

### 6.2 レビュー体制

- レビュー担当は**最低2名**。判定が割れたケースは記録して辞書改善に回す
- レビュー時に閲覧するのは**抽出されたセッションのみ**。全ログの閲覧権限を持たせない
- レビュー結果は `SafetyEvent.reviewed_by_human` と別途の監査テーブルに残す
- **臨床心理士・精神保健福祉士など資格保持者への月1回のレビュー委託を推奨**（内部だけで判定しない）

### 6.3 プライバシーとの両立

偽陰性の測定には本文の閲覧が必要ですが、常時保存は漏洩リスクです。

| 方針 | 内容 |
|---|---|
| 平常時 | `SafetyEvent` には**本文を保存しない**（`raw_excerpt_hash` のみ） |
| レビュー用 | `CompanionMessage.body` の既定90日保持を利用。抽出は保持期間内から行う |
| ユーザーへの開示 | プライバシーポリシーに「安全性の確認のため、匿名化した会話をごく一部、人が確認する場合があります」を明記し、**オプトアウトを提供** |
| オプトアウト時 | 抽出対象から除外する。ただし**リアルタイムの検知自体はオプトアウトできない**（安全機能であるため）。この点も明記 |

## 7. 規制上の整理 {#regulatory}

### 7.1 現在の位置づけ

日本には米国のような AI セラピー禁止法は2026年8月時点で存在しません。しかし方向は明確です（4州が完全禁止、Q1だけで70法案 — E-15）。**Woebot は150万ユーザーを抱えながら、FDA のマーケティング承認要件を満たすコストと困難を理由に2025年6月にサービスを終了しました**（E-26）。

### 7.2 とるべき立場

**「治療・診断をしない、症状に介入しない」という立場を、名称・機能・コピーの全レイヤーで一貫させる。**

| レイヤー | 現状 | 変更 |
|---|---|---|
| 機能名 | 「AIコーチ」 | **「壁打ち」**（職能名を外す）→ `08` |
| 自己記述 | 「あなた専用のアドバイス」 | 「考えを整理する相手」 |
| 出力 | 「〜を試してみませんか？」（行動指示） | 問い返しと選択肢の提示を主に → `08` |
| 対象 | 症状の言及に応答 | **症状・診断名の入力には応答せず、受診を案内** |
| 免責 | 入力欄下に常設（良い） | **維持**。加えて初回起動時に1回、全画面で明示 |

### 7.3 法務確認が必要な項目（宿題）

1. **プログラム医療機器（SaMD）該当性**: 「壁打ち」が疾病の診断・治療・予防に該当しないことの整理。厚労省のプログラム医療機器該当性ガイドラインに照らした自己評価と、必要なら照会
2. **利用規約**: 医療行為でないこと、危機時の対応の限界、通報を行わないこと、を明記
3. **未成年**: 年齢確認の要否。Character.AI は2025年10月に18歳未満のオープンエンドチャットを禁止した（E-25）。**最低限、未成年の利用を規約で扱うか、年齢に応じて壁打ちの利用可否を分けるかの判断が必要**
4. **B2B/教育機関向けに販売する場合**: 学校・企業が「安全でないツールを従業員/生徒に配った」責任を負うため、§6 の測定体制が販売条件になる可能性が高い

## 9. 計測

| 指標 | 定義 | 目標 |
|---|---|---|
| `block` 発火率 | 全壁打ち送信に対する割合 | （目標値を置かない。観測のみ） |
| `caution` 発火率 | 同上 | 同上 |
| **偽陰性件数** | 抽出レビューで「本来 block/caution」と判定された件数 | **0**。1件でも出たら辞書を即日更新 |
| 偽陽性率 | ユーザー報告「的外れだった」のうち `block`/`caution` 由来の割合 | 参考値。**下げることを目標にしない** |
| 窓口カードのタップ率 | `block` 表示に対する電話/リンクのタップ | 観測のみ（低くても機能失敗ではない） |
| 検知後の離脱 | `block` 後7日以内の再訪率 | 観測。極端に低ければコピーを見直す |

**重要**: `block` 発火率を「下げる」ことを KPI にしてはいけません。検知を弱めるインセンティブが生まれます。
