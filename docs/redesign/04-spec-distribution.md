# 04. 配信基盤仕様（ストア掲載とプッシュ通知）

**優先度: P0** / 対応課題: C-12, C-13

> **これが解けていないと、他のすべての機能が届きません。** 機能開発より先に着手すべき唯一の項目です。

---

## 1. 現状と問題

### 1.1 観察された事実

`/settings` でのブラウザ評価（2026-08-01）:

```
manifestHref                 : /manifest.webmanifest
serviceWorker 登録           : あり
apple-mobile-web-app-capable : なし
Notification.permission      : default（一度も要求されていない）
App Store / Google Play リンク : 0件
```

設定画面の通知手段は**メールリマインドのみ**（既定 21:30）。

### 1.2 これが致命的である理由

| # | 問題 | 根拠 |
|---|---|---|
| 1 | **獲得チャネルがない** | 競合は全員ネイティブで、ストア検索から数百万DLを取っている（Awarefy 100万、muute 150万、Upmind 200万超、Daylio 1,900万、Finch 1,250万）。PWA はストア検索に載らない |
| 2 | **有料獲得では回収できない** | テレヘルスD2CのCACは **$150〜$500**、有料ソーシャルCACは2020年比 +30〜60%。月330円（手数料後280円）では回収不能（E-27） |
| 3 | **プッシュが実質使えない** | 日次/週次習慣アプリで最強のリテンション手段。iOS の Web Push は**ホーム画面に追加済み**であることが前提で、到達率が構造的に低い |
| 4 | **メールは開封されない** | 通知手段がメールのみでは、週次点検・揺れイベントの D-1 通知（→ `05`）が届かない。**揺れ予報は通知が届かないと機能ごと成立しない** |
| 5 | **指名検索でも負けている** | 「ココロバランス」は一般社団法人ココロバランス研究所が占有（C-14） |

**特に4が重要です。** 新コンセプトの再訪トリガーは「揺れイベントの日付」であり、その日を知らせる手段がなければ、コンセプトそのものが動きません。

---

## 2. 方針

### 2.1 とる手段: 既存Webをネイティブでラップする

**Webアプリを捨てて作り直すのではなく、既存のWeb実装をネイティブシェルに載せます。**

| 選択肢 | 評価 |
|---|---|
| **A. ネイティブラッパー**（Capacitor 等でWebViewをラップし、通知・課金・ヘルス連携だけネイティブAPIを使う） | **推奨。** 既存資産を保持しつつストアとプッシュを獲得。追加開発が最小 |
| B. フルネイティブ再実装（Swift/Kotlin または React Native / Flutter） | 品質は最高だが、コストと期間が新機能開発を止める。この段階では過剰 |
| C. PWA のまま、iOS はホーム画面追加を促す | ホーム画面追加のコンバージョンは低く、ストア検索の獲得を諦めることになる。**却下** |

**A を選ぶ判断根拠**: 現時点の課題は「品質」ではなく「到達」です。到達を最小コストで解決し、獲得が回り始めてからネイティブ化の深度を上げます。

### 2.2 段階

| フェーズ | 内容 | 目的 |
|---|---|---|
| **P0-a** | ネイティブラッパー + プッシュ通知 + ストア掲載（iOS/Android） | 到達の確保 |
| **P0-b** | ストア掲載情報の最適化（ASO） | オーガニック獲得 |
| P1 | アプリ内課金（IAP）対応 | ストア経由の課金 → `10` |
| P2 | Apple Health / Google Fit の読み取り連携 | → §6 |

## 3. 要件: ネイティブラッパー

### 3.1 機能要件

| ID | 要件 |
|---|---|
| D-01 | iOS / Android のネイティブアプリとしてストアに掲載できる形式であること |
| D-02 | ネイティブのプッシュ通知（APNs / FCM）を受信・表示できること |
| D-03 | Google OAuth が**WebView 内ではなくシステムブラウザ/ネイティブSDK経由**で動くこと（Google は WebView 内の OAuth を拒否する） |
| D-04 | ディープリンクに対応: 通知タップ → アプリ内の特定画面（`shake_event/:id` 等）へ遷移 |
| D-05 | オフライン時に「接続がありません」の**アプリらしい**表示を出す（WebView の白画面を見せない） |
| D-06 | Web 側と同一のセッションを共有し、既存ユーザーが再ログインなしで移行できること |
| D-07 | Web 版も並行して提供を続ける（既存ユーザーとPC利用のため） |
| D-08 | アプリのバージョンと Web のバージョンの不整合時に、強制アップデート案内を出せる仕組み |

### 3.2 iOS 審査で問題になりうる点（事前対策）

| リスク | 対策 |
|---|---|
| **「WebViewをラップしただけのアプリ」としてリジェクト**（Guideline 4.2 Minimum Functionality） | ネイティブ機能を実装して差別化: ①プッシュ通知、②ウィジェット（今週の備え1つを表示）、③Apple Health 連携、④共有シート経由での揺れイベント登録。**最低2つは必須** |
| **メンタルヘルス関連の審査厳格化** | 免責・相談窓口を**初回起動時に全画面で1回表示**。App Store の年齢制限とカテゴリを適切に設定 |
| **外部課金への誘導** | Web の Stripe 決済リンクをアプリ内から見せない。IAP を実装するまでは**アプリ内で課金導線を出さない** → `10` |
| **医療的主張** | ストア説明文に「診断」「治療」「改善」を使わない → `03#regulatory` |

### 3.3 Android 側

- Google Play の**「健康とフィットネス」カテゴリの宣言**が必要。健康データの取り扱いをデータセーフティ セクションに正確に記載
- Play の「機微な権限」は要求しない（連絡先・位置情報は不要な設計にする）

## 4. 要件: プッシュ通知

### 4.1 通知の全リスト

**通知は少なく、意味があるものだけ。** 通知過多は即アンインストールの理由になります。

| ID | 名称 | タイミング | 既定 | 文面案 |
|---|---|---|---|---|
| `N-01` | 週次点検 | 週1回・日曜 21:00（時刻変更可） | **ON** | 「今週、支えになったのはなんでしたか？（30秒）」 |
| `N-02` | 備えの提案 | 揺れイベント D-14 の 20:00 | ON | 「〈◯◯〉まで2週間。ひとつだけ、備えを考えてみませんか」 |
| `N-03` | 備えのリマインド | `accepted` な備えの `due_date` 当日 20:00 | ON | 「〈Aさんに連絡する〉、今日までにしてみますか」 |
| `N-04` | 前日 | 揺れイベント D-1 の 21:00 | ON | 「明日は〈◯◯〉ですね。支えリストを用意しました」 |
| `N-05` | 当日 | 揺れイベント D-0 の朝 8:00 | ON | 「今日です。あなたには他にこれがあります」 |
| `N-06` | ふりかえり | 揺れイベント D+3 の 20:00 | ON | 「〈◯◯〉から3日。どうでしたか？（3タップ）」 |
| `N-07` | ペアの承認 | ペアの相手が柱を承認したとき（即時、ただし1日1通まで集約） | ON | 「◯◯さんが、あなたの〈木曜のバンド〉を確かな柱として承認しました」 |
| `N-08` | ペア招待 | 招待を受けたとき | ON | 「◯◯さんからペアの招待が届いています」 |

**これで全部です。** 以下は**実装しません**。

| 実装しない通知 | 理由 |
|---|---|
| 「3日間記録がありません」 | 原則1（判定しない）・原則5（毎日を要求しない）に違反 |
| 「連続記録が途切れます」 | 原則2（数えない） |
| 「他のユーザーは今週◯回記録しています」 | 比較による圧 |
| 一般的なウェルネスTips の定期配信 | 開封率が落ち、通知OFF率を上げるだけ |
| キャンペーン・課金訴求のプッシュ | 通知を広告に使うと全通知の信頼が落ちる |

### 4.2 通知の設計原則

| 原則 | 内容 |
|---|---|
| **催促は1回だけ** | 未実施でも再送しない（`N-01` は翌週まで待つ、`N-06` は1回のみ） |
| **上限を設ける** | 1日最大2通、1週最大5通。超える場合は優先度順に間引く |
| **判定しない文面** | 「まだやっていません」「遅れています」を使わない |
| **通知の中身に価値を入れる** | 「開いてください」ではなく、通知文だけで少し役に立つ（`N-05` の文面など） |
| **静音時間** | 22:30〜07:30 は送らない（`N-01` の 21:00 は境界内）。ユーザーのタイムゾーンで判定 |
| **粒度の高いOFF** | 通知種別ごとに個別ON/OFF可。「全部OFF」も1タップでできる |

### 4.3 権限要求のタイミング

**初回起動時に要求してはいけません。** 拒否されたら二度と要求できません（OS仕様）。

```
オンボーディング
  → 柱を1つ登録
  → 揺れそうな日を1つ登録        ← ここまで価値を体験させる
  → 「〈◯◯〉が近づいたらお知らせします。通知を許可しますか？」
  → OS の許可ダイアログ
```

事前説明画面（プレプロンプト）を必ず挟み、**なぜ必要かを具体的な自分のイベント名で説明する**こと。拒否された場合はメール通知にフォールバックし、設定画面から後で有効化できる導線を残す。

### 4.4 メール通知の扱い

現行のメールリマインドは**廃止せず、フォールバックとして維持**します。

| 条件 | 通知手段 |
|---|---|
| プッシュ許可あり | プッシュのみ（メールは送らない。二重送信はしない） |
| プッシュ拒否／Web版利用 | メール |
| 重要な通知（`N-04` `N-05`） | プッシュ許可があってもメールを併送する設定を任意で提供 |

## 5. ASO（ストア最適化）

### 5.1 なぜ重要か

**ストア内検索が、このプロダクトで唯一 CAC が実質ゼロになるチャネルです。** 有料広告では月330円を回収できません（§1.2）。

### 5.2 キーワード戦略

**「メンタル」「気分記録」で戦わない。** そこは Daylio / Awarefy / Upmind / Apple Health が占めています。**イベント名で入る**のが新コンセプトの利点です。

| 群 | キーワード例 | 狙い |
|---|---|---|
| **推し活の危機** | 推し 卒業 / 活動休止 つらい / 推しロス / ラストライブ / ファン 別れ | 検索需要が明確で、競合が0 |
| **仕事の転機** | 異動 不安 / 退職 不安 / 契約更新 / 繁忙期 メンタル | |
| **関係の転機** | 遠距離 / 引っ越し 不安 / 失恋 立ち直る | |
| **試験** | 合否発表 不安 / 受験 メンタル | |
| 汎用（副次） | セルフケア / 心の支え / 居場所 | 主戦場にしない |

### 5.3 掲載物の要件

| 項目 | 方針 |
|---|---|
| アプリ名 | `〈サービス名〉- 揺れる日に備える` 形式（サブタイトルにコンセプトを入れる） |
| スクリーンショット1枚目 | **揺れイベントの当日画面（支えリスト）**。円グラフを1枚目に置かない |
| 説明文 | 冒頭3行で「揺れる日に備える」を言い切る。医療的主張を書かない（`03#regulatory`） |
| プレビュー動画 | イベント登録 → 備え → 当日 の3カットのみ |
| カテゴリ | 健康&フィットネス（メディカルではない） |
| 年齢設定 | §3.2 の未成年判断に従う → `03#regulatory` |
| レビュー依頼 | **ふりかえりで `was_supported = yes` を選んだ直後に1回だけ**要求（最も満足度が高い瞬間） |

## 6. Apple Health / Google Fit 連携（P2）

### 6.1 方針: 競合せず、入力として使う

Apple Health の **State of Mind** は気分ログと睡眠・運動との相関表示を**OS標準で無料提供**しています（E-12）。円グラフのコア価値はすでにOSにあります。

**したがって、気分の記録では戦いません。OSが持っているデータを読み込み、こちらは「柱」だけに専念します。**

| 読む（Read） | 用途 |
|---|---|
| State of Mind（気分ログ） | 週次点検の補助。「先週の水曜、気分が落ちていたようです。何かありましたか？」の起点 |
| 睡眠時間 | `habit` 型の柱「睡眠」の自動更新（ユーザーに入力させない） |
| ワークアウト | 同様に `habit` 型の自動更新 |

| 書かない（Write） | 理由 |
|---|---|
| 気分データを Health に書き戻す | 二重管理になる。**読むだけにする** |

### 6.2 実装上の注意

- 権限は**必要になった瞬間に個別に要求**する（オンボで全部要求しない）
- 連携なしでも全機能が使えること（連携は補助）
- **iOS 側の仕様変更リスクを前提にする**。Apple は 2026年2月に AI 健康コーチ（Health+ / Project Mulberry）を iOS 27 から外し縮小したと報じられており（E-28）、OS側の動きは予測できない。**連携を前提とした機能を作らない**

## 7. 受入基準

| # | 基準 |
|---|---|
| D-A-01 | iOS / Android のストアにアプリが掲載され、検索で発見できる |
| D-A-02 | `N-01`〜`N-08` の全通知が実機に届き、タップで該当画面に遷移する |
| D-A-03 | 通知の静音時間（22:30〜07:30）と1日2通/週5通の上限が機能する |
| D-A-04 | 通知権限の要求が、オンボで揺れイベントを1件登録した**後**に発生する |
| D-A-05 | プッシュ拒否時にメールへフォールバックし、二重送信されない |
| D-A-06 | Google OAuth がネイティブアプリで成功する（WebView 内で失敗しない） |
| D-A-07 | 既存 Web ユーザーがアプリ初回起動時に再ログインを求められない |
| D-A-08 | IAP 未実装の段階で、アプリ内に外部課金への導線が存在しない |
| D-A-09 | オフライン時に白画面ではなく専用画面が出る |
| D-A-10 | ストア説明文・スクリーンショットに「診断」「治療」「改善」の語がない |

## 8. リスクと緩和

| リスク | 影響 | 緩和 |
|---|---|---|
| iOS が「WebViewラッパー」としてリジェクト | 到達計画が全て止まる | §3.2 のネイティブ機能を**最低2つ実装してから提出**。ウィジェットが最も評価されやすい |
| ストア審査でメンタルヘルス表現を指摘 | 差し戻しで数週間ロス | `03#regulatory` の表現整理を審査提出**前**に完了させる |
| プッシュ許可率が低い | 揺れ予報が機能しない | §4.3 のプレプロンプト設計。許可率を計測し、40%を下回るなら文面をA/Bテスト |
| ASO キーワードに検索需要がない | オーガニック獲得が立たない | 実装前にストアのキーワードツールで検索ボリュームを確認。needs 検証を先に |
| ネイティブ化の工数が新機能を圧迫 | 揺れ予報のリリースが遅れる | ラッパー方式を選ぶ理由がこれ。フルネイティブ化はしない |
