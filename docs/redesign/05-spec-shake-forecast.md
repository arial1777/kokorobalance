# 05. 揺れ予報 仕様

**優先度: P1（新規開発の主機能）** / 対応課題: C-06, C-08, C-17

> このアプリが「気分記録アプリ」というカテゴリから抜け出すための機能です。他の施策が既存資産の組み替えであるのに対し、これだけが新規開発です。

---

## 1. 目的と根拠

### 1.1 何を解くのか

現行アプリは**事後の可視化**しかしていません。しかし LP が描いているのは危機そのものです。

> 「恋人とうまくいかなかった夜」／「**推しの卒業発表を見た日**」／「仕事で大きなミスをした日」

**これらの多くは、事前に日付がわかります。** 推しの卒業発表、契約更新、異動発表、退職日、合否発表、引っ越し。揺れ予報は、**事前にわかる揺れに対して、事前に備える**機能です。

### 1.2 根拠

| # | 根拠 | 出典 |
|---|---|---|
| 1 | 気分アプリは **collection（収集）と reflection（振り返り）は豊富だが、preparation と action の支援が構造的に欠落**している（商用32アプリの機能分析） | E-08 |
| 2 | 実利用者インタビューでの最大の不満は「**自分のデータをどう解釈すべきかの示唆がアプリから提供されない**」 | E-07 |
| 3 | 離脱者の**39%が「測定可能な改善がなかった」**を理由に挙げる | E-18 |
| 4 | 事前の if-then 型の計画（implementation intentions）は行動変容技法として効果量が確立されている | **E-29（未検証。引用前に一次確認）** |
| 5 | 推し活層は 20代女性の45%。推し活支出は物価高でも**54.0%が全く削らない** | E-14 |

### 1.3 副次的な狙い

| 狙い | 内容 |
|---|---|
| **再訪理由の獲得** | 開くべき日が自明になる。日次記録が解けなかったリテンション問題に別角度から答える |
| **カテゴリの脱出** | 「メンタルの防災」は Apple Health / Daylio / Finch のいずれもいない空きポジション |
| **推し活層を敵にしない** | 「推しに依存するな」ではなく「**卒業発表の日に備えよう**」。同じ機能で真逆の温度 |
| **課金理由の明確化** | 「あの日に備える」は支払う瞬間が具体的 |
| **ASO の入口** | 「推し 卒業」「異動 不安」等、競合ゼロの検索キーワードで入れる → `04#aso` |

## 2. ユーザーストーリー

### 2.1 主ストーリー（推し活）

> 私は VTuber のファンで、来月15日に卒業配信がある。今からずっと落ち込んでいる。
> アプリに「〈◯◯〉の卒業配信 / 9月15日」を登録した。
> 2週間前、アプリが「ひとつだけ備えを考えませんか」と聞いてきた。提案は3つ。私は「同じ推しを追っている友達に、卒業配信のあと通話しないか聞いてみる」を選んだ。
> 数日後、思い出して連絡した。相手も同じことを考えていた。
> 前日の夜、アプリが「明日ですね」と教えてくれた。開くと、私を支えているものが並んでいた。**「卒業配信のあと、Aさんと通話する（約束済み）」が一番上にあった。**
> 当日はやっぱり泣いた。でも通話して、2人で泣いた。
> 3日後、アプリが「どうでしたか」と聞いてきた。私は「支えられた」を選び、「Aさん」を選んだ。

### 2.2 副ストーリー（仕事）

> 来週、異動の発表がある。希望が通らない気がしている。
> 「異動発表 / 8月20日」を登録した。備えの提案は「社外の友人に連絡する」「趣味の時間を先に予定に入れる」「相談できる同僚を1人思い出す」。
> 発表は希望と違った。でも当日アプリを開いたら、「木曜のバンド」「学生時代のAさん」「土曜の朝の散歩」が並んでいた。**仕事以外に3つあることを、その日に思い出せた。**

### 2.3 日付が未定のケース

> 恋人と別れそうな気がする。でも日付なんてわからない。
> 「関係の転機 / 日付は未定」で登録した。アプリは日付を聞き直さず、週次点検のときに一度だけ「そろそろですか？」と聞いてくれた。

## 4. ①登録

### 4.1 入力の設計思想

**自由記述を要求しません。** 「揺れそうな日」を自分で言語化することは、記録より認知負荷が高い可能性があります（→ `01-concept.md#12`）。テンプレートから選ぶ形にします。

### 4.2 テンプレート一覧

**テンプレは追加・調整が容易な設定として持つこと**（コードにハードコードしない）。ユーザーの登録実績から需要の高いものを増やしていきます。

### 4.3 登録フロー

```
[揺れ予報タブ] → [＋ 揺れそうな日を追加]
   │
   ├─ Step1: どんな日？        （カテゴリ → テンプレの2段選択。全23個を一覧で見せない）
   ├─ Step2: いつ？            （カレンダー / 「まだわからない」 のトグル）
   ├─ Step3: どのくらい揺れそう？（3段階。絵文字ではなく言葉:「少し」「けっこう」「かなり」）
   └─ Step4: 揺れるかもしれない柱を選ぶ（任意・スキップ可。既存の柱から複数選択）
   　　　　　→ 完了。「〈◯◯〉まで あと32日」
```

**要件**

| ID | 要件 |
|---|---|
| S-01 | Step1〜3 は必須、Step4 は任意。**3タップ＋日付選択で完了できること** |
| S-02 | Step2 で「まだわからない」を選べる（`is_date_certain = false`） |
| S-03 | Step3 の表現に絵文字（😢等）を使わない。**揺れの大きさを顔で表現すると判定に見える** |
| S-04 | Step4 で選ばなくても、後述の支えリスト生成は動くこと |
| S-05 | 過去の日付は登録できない（ただし「思い出す日」は**来年の同じ日**として登録できる） |
| S-06 | 同時に有効な `ShakeEvent` は最大10件。それ以上は「多すぎると備えが散ります」と伝えて上限とする |
| S-07 | `title` は自由記述時のみ入力。テンプレ選択時は自動生成し、後から編集可 |
| S-08 | `title` 保存時にセーフティ判定を通す（→ `03`） |

### 4.4 オンボーディングでの必須化

原則4（空の状態を作らない）に基づき、**オンボーディングで揺れイベントを1件登録させます**。

```
オンボーディング（新）
  1. 「いま、あなたを支えているものは？」→ 柱を2〜4件登録（→ 07）
  2. 「この先、心が揺れそうな日はありますか？」
       → テンプレ一覧を category ごとに提示
       → 「いまは思いつかない」も選べる（この場合は §4.6 へ）
  3. 通知許可（→ 04#permission）
  4. 完了 → 「今週」タブへ。すでに備えが1つ提案されている状態
```

**「いまは思いつかない」を選んだユーザーの扱い**は §4.6。

### 4.5 期間型イベント

`work_busy_season` `life_alone` のように、点ではなく期間で揺れるケースがあります。

- 内部的には**開始日を `event_date` とする単一の `ShakeEvent`** として扱う（期間を第一級の概念にしない）
- `duration_days` を任意属性として持ち、当日画面を期間中は継続表示する
- 期間中の通知は**開始日と中間日の2回まで**

### 4.6 「思いつかない」ユーザーの扱い

これが**コンセプト最大のリスク**です（→ `01-concept.md#12`）。

| 対策 | 内容 |
|---|---|
| **カレンダーからの推測を提案しない** | 端末カレンダーの読み取り権限を要求すると心理的抵抗が大きい。**やらない** |
| **柱から逆算して問う** | 登録済みの柱のうち `is_fragile = true` のものについて「〈推し〉に、この先なにか予定はありますか？」と1問だけ聞く |
| **季節の候補を出す** | 年末年始・GW・お盆・年度末など「ひとりで過ごすかもしれない日」を候補として静かに提示 |
| **週次点検で拾う** | 点検時に「この先、気が重い予定はありますか？」を**4週に1回だけ**出す（毎週聞かない） |
| **それでもゼロなら** | 週次点検だけのユーザーとして成立させる（→ `06`）。**揺れイベントを登録しないことを失敗として扱わない** |

## 5. ②備え（PrepAction）

### 5.1 タイミング

| 日 | 動作 |
|---|---|
| **D-14** | `status: planned → prepping`。備えの候補を3件生成し、`N-02` を送信 |
| D-14 〜 D-1 | ユーザーが1件を `accepted` にする。`due_date` を設定 |
| `due_date` 当日 | `N-03` を送信 |
| 完了操作時 | `done`。**次の備えを1件だけ提案**（週1ペース） |
| D-0 | 未完了の `accepted` は `skipped` に。**通知しない** |

**`expected_shake = 3` の場合は D-21 から開始**します（大きな揺れには準備期間を長く取る）。

### 5.2 同時に1つだけ、という制約

```
1つの ShakeEvent に対して state = accepted の PrepAction は同時に1件まで
```

理由: 複数の宿題を同時に出すと「やることリスト」になり、原則1（判定しない）に違反します。**未完了の宿題が積み上がる画面を作ってはいけません。**

### 5.3 備えの生成ロジック

**ルールベースを主、AIを従とします。** AI 単独に生成させると、競合レビュー最多の不満「定型文・オウム返し」（E-09）を再生産します。

```
候補生成
  ├─ [1] ルールベース（テンプレ × 柱の状態）  ← 主。必ず2件以上
  └─ [2] AI 生成                              ← 従。1件のみ、Pro のみ
       ↓
  3件を提示（うち最低2件はルール由来）
```

#### ルールベースの生成規則

`ShakeEvent.category` と、ユーザーの柱の状態から候補を選びます。

| 条件 | 生成する備え（例） |
|---|---|
| 揺れる柱が `place` で、他に `place` 型の確かな柱がある | 「〈◯◯〉に、この2週間で一度顔を出す」 |
| 揺れる柱が `place`／`relation` で、`育て中` の柱がある | 「〈Aさん〉に、近いうち会えないか連絡してみる」 |
| 確かな柱が2件以下 | 「昔つながっていた人を1人思い出して、名前だけ登録する」（柱の新規追加を促す） |
| `category = oshi` かつ 同カテゴリの `place` 柱がある | 「当日のあと、同じものを好きな人と話す約束をする」 |
| `category = oshi` かつ 同カテゴリの柱がない | 「同じものを好きな人が集まる場所を1つ探しておく」 |
| `category = work` | 「仕事の外にある柱を1つ、当日の前後に予定として入れる」 |
| `category = exam` `health` | 「結果を聞いたあと、最初に連絡する人を決めておく」 |
| `category = relationship` | 「その人以外に、話せる相手を1人思い出しておく」 |
| ペアがいる | 「ペアの相手に、その日が近いことを伝えておく」（→ `09`） |
| 常に候補に含める（最終手段） | 「当日の予定を、あえて何も入れないでおく」 |

**要件**

| ID | 要件 |
|---|---|
| S-10 | ルールベースで**必ず2件以上**生成できること（AI が使えない環境でも機能する） |
| S-11 | 生成された `body` は 60文字以内、**動詞で終わる具体的な1行**であること |
| S-12 | 「〜しましょう」「〜すべきです」を使わない。「〜してみる」「〜を考えてみる」 |
| S-13 | ユーザーが**自分で備えを書ける**こと（`source = user`）。テンプレに縛らない |
| S-14 | 同じ `ShakeEvent` で、過去に `skipped` にした備えを再提案しない |
| S-15 | AI 生成分は Pro のみ。Free でもルールベース2件で完結すること（**Free を機能不全にしない**） |

**「選ばなくても大丈夫です」を明示することが原則1の実装です。**

`accepted` 後:

```

│  いま備えていること                       │
```

## 6. ③当日（支えリスト）

**この機能の核心です。**

### 6.1 支えリストの確定タイミング

**D-1 の 21:00 に生成し、`support_list_snapshot` としてイベントに固定保存します。**

理由: 当日にリアルタイム生成すると、①AI障害・通信障害で最も必要な瞬間に出せない、②内容が毎回変わって「用意されていた感」がない。**事前に用意されていたことが体験の本質**です。

### 6.2 内容と並び順

| 順 | 内容 | 条件 |
|---|---|---|
| 1 | **完了した備え**（`done`）。「約束済み」バッジ付き | あれば最優先 |
| 2 | **確かな柱**（`verified` な `place` / `relation`）。ただし `affected_pillar_ids` に含まれるものは除く | 最大4件。直近の点検で `level` が高い順 |
| 3 | **習慣**（`habit`）で、直近4週の点検に出てきたもの | 最大2件 |
| 4 | `skipped` になった備え。「まだ手はあります」として | あれば最後 |
| 5 | 相談窓口への静かな導線 | **常に最下部に置く** |

**除外規則**: `affected_pillar_ids`（揺れる柱）は支えリストに載せません。「揺れている当のものを支えとして提示する」のは無意味です。

### 6.4 要件

| ID | 要件 |
|---|---|
| S-20 | D-1 21:00 に `support_list_snapshot` を確定し、**以降は再生成しない** |
| S-21 | D-0 の朝 8:00 に `N-05` を送信。通知タップで直接この画面へ |
| S-22 | この画面は**通信が切れていても表示できる**こと（スナップショットをローカルにキャッシュ） |
| S-23 | 「あなたには、これがあります」の断定を、**確かな柱が0件の場合は使わない**（→ §6.5） |
| S-24 | 相談窓口を**常に最下部に置く**。検知の有無に関わらず、揺れの当日は必ず出す |
| S-25 | 円グラフ・数値・スコアをこの画面に置かない |
| S-26 | 期間型イベントの場合は期間中この画面を表示し続ける |
| S-27 | 揺れの当日に**壁打ちの利用回数制限を解除する**（Free でも当日は無制限）→ `08` |

### 6.5 支えが少ないユーザーの当日画面

**最も慎重な設計が必要な箇所です。** 確かな柱が0〜1件のユーザーに「あなたには、これがあります」と言えません。

| 確かな柱の数 | 見出し |
|---|---|
| 2件以上 | 「あなたには、これがあります。」 |
| 1件 | 「今日は、これがあります。」 |
| **0件** | **「今日はしんどい日かもしれません。無理に何かしなくて大丈夫です。」**（リストは出さず、習慣と相談窓口のみ） |

0件の場合に**「柱を増やしましょう」と言ってはいけません**（最悪のタイミングでの宿題）。

---

## 7. ④ふりかえり（ShakeReview）

### 7.1 タイミング

- **D+3 の 20:00** に `N-06` を1回だけ送信
- D+1 〜 D+7 の間、「今週」タブの優先度3として表示
- D+8 で自動アーカイブ。**未実施でも催促しない**

「D+1 ではなく D+3」の理由: 当日〜翌日はまだ揺れの中にいるため、振り返りを要求するのは負荷です。

### 7.2 入力（3タップ）

```
┌──────────────────────────────────────────┐
│  ◯◯の卒業配信 から3日。                   │
│                                          │
│  1. 実際、どのくらい揺れましたか？         │
│     [ 少し ] [ けっこう ] [ かなり ]      │
│                                          │
│  2. 支えられた感じはありましたか？         │
│     [ あった ] [ 少し ] [ なかった ]      │
│                                          │
│  3. どれが効きましたか？（複数選択・任意） │
│     □ Aさんと通話する                     │
│     □ 木曜のバンド                        │
│     □ 学生時代のBさん                     │
│     □ 土曜の朝の散歩                      │
│                                          │
│  ＋ ひとこと残す（任意）                   │
│                                          │
│                              [ 終わり ]   │
└──────────────────────────────────────────┘
```

### 7.3 完了後の返し

**ここが「効果の実感」を作る唯一の場所です。** 離脱理由の39%が「測定可能な改善がなかった」（E-18）である以上、抽象的な改善ではなく**具体的な記憶**を残します。

| `was_supported` | 返す内容 |
|---|---|
| `yes` | 「**Aさんと通話する** が効いた、と残しました。次に揺れそうな日が来たら、まずこれを思い出します。」<br>→ 続けて**ストアレビュー依頼を1回だけ**（→ `04#aso`） |
| `partly` | 「**木曜のバンド** が少し効いた、と残しました。次はここから考えてみます。」 |
| `no` | 「そうでしたか。書いてくれてありがとうございます。**効かなかったことも、次の手がかりになります。**」<br>→ 相談窓口を静かに併記。**「では次はこうしましょう」と提案しない** |

`no` の場合に代替案を即座に出すのは、原則1違反です（うまくいかなかった人にさらに宿題を出す）。

### 7.4 次回への反映

| 反映先 | 規則 |
|---|---|
| 備えの提案順 | `helped_pillar_ids` に含まれた柱を使う備えを、次回同カテゴリのイベントで**上位に出す** |
| 支えリストの並び | `helped_pillar_ids` の柱を上位に |
| 柱の承認 | `helped_pillar_ids` に選ばれた柱は、承認の補強シグナルとする（→ `07`） |
| `expected_shake` の補正 | `felt_shake` と `expected_shake` の差を蓄積し、次回同テンプレの既定値に反映（**ユーザーには見せない**） |

`02-domain-model.md` の `ShakeEvent` / `PrepAction` / `ShakeReview` を参照。この仕様で追加が必要な属性:

| エンティティ | 追加属性 | 説明 |

## 9. バッチ処理

| ジョブ | 実行 | 処理 |
|---|---|---|
| `advance_shake_status` | 毎時（ユーザーTZを考慮） | 日付到達による `status` 遷移（→ `02#3.1`） |
| `generate_prep_candidates` | D-14（`expected_shake=3` は D-21）到達時 | 候補3件を生成し `N-02` を予約 |
| `snapshot_support_list` | D-1 の 21:00 | `support_list_snapshot` を確定し `N-04` を送信 |
| `notify_event_day` | D-0 の 08:00 | `N-05` |
| `notify_review` | D+3 の 20:00 | `N-06` |
| `archive_stale_events` | 日次 | D+8 経過の `passed` を `archived` に |
| `ask_undated_events` | 週次点検の生成時 | `is_date_certain = false` のイベントについて「そろそろですか？」を1件だけ添える |

**冪等性**: 全ジョブは再実行安全であること。通知は `(event_id, notification_id)` で重複送信を防ぐ。

## 10. エッジケース

| # | ケース | 挙動 |
|---|---|---|
| E-01 | 揺れイベントが同日に複数 | 「今週」タブは `expected_shake` が大きいものを表示。支えリストは**統合して1つ**出す |
| E-02 | 揺れイベントを当日に登録 | 備えのフェーズをスキップし、即座に支えリストを生成して表示 |
| E-03 | 揺れイベントの日付を後から変更 | `status` を再計算。既に確定した `support_list_snapshot` は破棄して再生成 |
| E-04 | 揺れる柱（`affected_pillar_ids`）を全部除外したら支えリストが0件 | §6.5 の 0件表示に落とす |
| E-05 | イベント登録直後に柱を全削除 | 同上 |
| E-06 | `event_date` が1年以上先 | 登録は許可。`planned` のまま置き、D-14 まで何もしない |
| E-07 | 「思い出す日」（命日等）の翌年 | ふりかえり完了後に「来年も登録しますか？」を1回だけ聞く |
| E-08 | 通知許可なし | メールにフォールバック（→ `04#4.4`）。アプリを開いたときに「今週」タブで拾う |
| E-09 | ふりかえりを D+8 以降にやりたい | アーカイブ済みイベントの詳細から実行可。ただし催促はしない |
| E-10 | 揺れイベントのタイトルにセーフティ検知 | 保存はする。保存完了時に相談窓口カード（→ `03#4`） |
| E-11 | 期間型イベントの期間が30日超 | 30日で打ち切る（それは「揺れる日」ではなく状態） |
| E-12 | 同じテンプレで短期間に大量登録（10件上限に達する） | 上限メッセージ。「多すぎると備えが散ります」 |

## 11. 受入基準

| # | 基準 |
|---|---|
| SF-A-01 | テンプレ選択 + 日付 + 揺れの大きさの**3タップ＋日付選択**でイベント登録が完了する |
| SF-A-02 | 「まだわからない」で日付未定のイベントが登録でき、D-14 バッチの対象外になる |
| SF-A-03 | D-14 に備え候補が3件（うちルール由来が2件以上）生成され、通知が届く |
| SF-A-04 | `accepted` な備えが同時に1件を超えない |
| SF-A-05 | D-1 21:00 に支えリストが確定し、**以降内容が変わらない** |
| SF-A-06 | 支えリストが**オフラインでも表示できる** |
| SF-A-07 | 支えリストに `affected_pillar_ids` の柱が含まれない |
| SF-A-08 | 確かな柱が0件のとき、§6.5 の専用表示になり「柱を増やしましょう」が出ない |

| SF-A-10 | D+3 にふりかえり通知が**1回だけ**届き、未実施でも再送されない |
| SF-A-11 | `was_supported = no` のとき、代替案の提案が出ない |
| SF-A-12 | 支えリスト画面と当日通知に相談窓口が含まれる |
| SF-A-13 | 進捗バー・達成率・スコア・ストリークがこの機能のどの画面にも存在しない |
| SF-A-14 | AI が利用不可の状態でも、ルールベースのみで機能が完結する |

## 12. 計測

| 指標 | 定義 | 目標 |
|---|---|---|
| **イベント登録率** | オンボ完了者のうち `ShakeEvent` を1件以上登録 | **70%** |
| 備え accept 率 | 候補提示に対する `accepted` | 50% |
| **備え完了率** | `accepted` に対する `done` | **40%** |
| 当日画面到達率 | `today` になったイベントのうち、当日に画面を開いた率 | 60% |
| ふりかえり実施率 | `passed` に対する `ShakeReview` 作成 | 50% |
| **北極星: 支えられた率** | `was_supported ∈ {yes, partly}` / 全ふりかえり | **60%** |
| 2件目登録率 | 1件目のふりかえり完了者が、次のイベントを登録する率 | 50%（**リピートの本質指標**） |
| カテゴリ別分布 | `category` ごとの登録数 | 観測（テンプレ拡充の判断材料） |
| 日付未定率 | `is_date_certain = false` の割合 | 観測（高すぎるなら §4.6 を強化） |

**注視すべき失敗シグナル**: イベント登録率が 40% を下回る場合、`01-concept.md#12` のリスク1（言語化の認知負荷）が現実化しています。テンプレの見せ方を変えるか、コンセプトの再検討が必要です。
