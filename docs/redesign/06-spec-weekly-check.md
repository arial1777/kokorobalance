# 06. 週次点検 仕様（記録機能の再設計）

**優先度: P1** / 対応課題: C-04, C-05, C-06, C-07

現行の「毎日の記録」＋「円グラフ」を、**週1回の点検**に置き換えます。

---

## 1. なぜ日次をやめるのか

| # | 根拠 | 出典 |
|---|---|---|
| 1 | 日本の未利用理由 第2位は「**記録が面倒（28.8%）**」 | E-21 |
| 2 | メンタルヘルスアプリの30日継続率 中央値 **3.3%**、トラッカー型でも **6.1%** | E-17 |
| 3 | self-monitoring は "oppressive"（抑圧的）"punishy"（罰的）と体験され、**罪悪感と恥**を生む。"tedious" "boring" "hard work" とも表現される（n=1,768） | E-06 |
| 4 | 気分モニタリング介入は最新メタ分析（2026年1月）で**効果が確認されていない**。著者は「治療介入ではなく**アウトカム測定手段**として位置づけるべき」と結論 | E-16 |
| 5 | ユーザーは**ネガティブな気分を記録しない**。「ポジティブな気分だけを記録することを好んだ」ユーザーが存在し、記録データは構造的に歪む | E-07 |
| 6 | 日次記録の勝者は確定済み（Daylio 1,900万DL の2タップ記録、Apple Health の State of Mind） | E-19, E-12 |

**結論**: 日次記録は「勝てず、効かず、嫌われる」三重苦です。**やめることが差別化になります。**

### 逆説的な差別化

> **「毎日開かなくていいアプリです。週に1回、それで足ります。」**

これをコピーで明示的に宣言します。全競合が「毎日続けましょう」と言っている市場で、唯一これを言うプロダクトになります。

## 2. 仕様

### 2.1 タイミング

| 項目 | 値 |
|---|---|
| 頻度 | 週1回 |
| 通知 | 日曜 21:00（`N-01`、時刻はユーザー変更可） |
| 所要 | **30秒 / 3タップ**を目標 |
| 週の定義 | `User.week_start_day`（既定は月曜始まり）。通知は週末の夜 |
| 未実施時 | **催促しない。** 翌週まで待つ |
| 遅れて実施 | 週の途中でも可。過去の週を遡って入力することはできない（1週前まで許容） |

### 2.2 画面と入力

```
┌──────────────────────────────────────────┐
│  今週の点検                               │
│  8/26 - 9/1                              │
│                                          │
│  この1週間、支えになったのは？             │
│  （いくつでも / なくても大丈夫です）        │
│                                          │
│  ── 居場所 ──                             │
│  [ 木曜のバンド ]  [ ◯◯推し界 ]           │
│                                          │
│  ── 相手 ──                               │
│  [ Aさん ]  [ 同僚のBさん ]  [ 妹 ]        │
│                                          │
│  ── 習慣 ──                               │
│  [ 睡眠 ]  [ 朝の散歩 ]                    │
│                                          │
│  ＋ 新しく追加する                         │
│                                          │
│  ▸ ひとこと残す（任意）                    │
│                                          │
│                            [ 終わり ]     │
└──────────────────────────────────────────┘
```

### 2.3 タップの段階

現行アプリの「もう一度タップで度合いが上がります」を踏襲します。

| タップ回数 | `level` | 表示 |
|---|---|---|
| 0（未選択） | **保存しない** | 通常 |
| 1 | 1 | 薄く塗る |
| 2 | 2 | 中間 |
| 3 | 3 | 濃く塗る |
| 4 | 0（選択解除） | 通常に戻る |

**重要**: **「支えにならなかった」を記録させません。** 選ばれなかったものは単に保存しないだけで、「なし」として記録しません。ネガティブ記録の回避が継続の最大障壁である（E-07）ためです。

### 2.4 要件

| ID | 要件 |
|---|---|
| W-01 | **0件でも保存できる**（「今週は思いつかない」で完了可）。0件保存を失敗として扱わない |
| W-02 | `mood_note` は任意・**既定で折りたたみ**（現行の「揺れた出来事」の良い設計を踏襲） |
| W-03 | `mood_note` 保存時にセーフティ判定を通す（→ `03`） |
| W-04 | 点検画面から**その場で柱を追加できる**（→ `07`）。設定画面に飛ばさない |
| W-05 | 柱が多い場合（10件超）、直近4週で選ばれた順に並べ、残りは「もっと見る」に畳む |
| W-06 | 完了後に**祝わない**。紙吹雪・派手なアニメーション・「素晴らしい！」を出さない |
| W-07 | 進捗率・ストリーク・スコアを表示しない |
| W-08 | 1週前までは遡って入力できる。それ以前は不可（記憶の精度が落ち、かつ義務感を生む） |
| W-09 | 同一週の点検は**上書き編集可能**（`(user_id, week_start)` で一意） |

### 2.5 完了後の返し

`level` 合計が最も高かった柱を1つ、**評価せずに**言及します。

| 状態 | 文面 |
|---|---|
| 1件以上選択 | 「今週は **木曜のバンド** が大きかったんですね。記録しました。」 |
| 0件選択 | 「そういう週もあります。記録しました。」 |
| 4週連続で同じ柱が最上位 | 「**木曜のバンド** が4週続けて支えになっています。」（→ 承認シグナル、`07`） |

**禁止**: 「他の柱も育てましょう」「偏っています」「先週より少ないですね」

### 2.6 揺れイベントの拾い上げ

4週に1回だけ、点検の最後に1問を追加します。

```
▸ この先、気が重い予定はありますか？
   [ ある ] [ いまはない ]
```

`ある` を選んだら `05` の登録フローへ。**毎週聞きません**（毎週聞くと催促になる）。

また、`is_date_certain = false` の揺れイベントがある場合、点検時に1件だけ「〈◯◯〉、そろそろですか？」を添えます。

## 3. 円グラフの扱い

### 3.1 主画面から撤去する

| 理由 | 根拠 |
|---|---|
| 同じ機能が **Apple Health の State of Mind として OS に無料で内蔵済み** | E-12, C-15 |
| 実データになるまで数週間かかる（現行アプリは「はじめの診断を含む表示です」の注記が常設） | C-05 |
| 構成比を見せることは「あなたの構成は偏っている」という**判定**として届く | 原則1, E-06 |
| 記録カテゴリが固定されるため**毎週ほぼ同じ形になり、情報を生まない** | C-06 |

### 3.2 移設先

**「ふりかえり」タブの奥**に移します。削除はしません（作った資産であり、見たい人はいる）。

```
ふりかえり タブ
├── 今週のまとめ            ← 週次点検の結果を1画面で
├── 柱の一覧               ← 確かな柱 / 育て中 / 習慣（→ 07）
├── 揺れの記録             ← 過去の ShakeReview 一覧
└── ▸ 構成の推移を見る      ← ここに円グラフ・棒グラフ・期間切替（折りたたみ）
```

### 3.3 表示規則（移設後）

| ID | 要件 |
|---|---|
| W-10 | 円グラフは**折りたたみの内側**に置く。タブを開いた直後には見えない |
| W-11 | **点検が4回以上ないと表示しない**（タブ自体を出さない）。「データがありません」を見せない = 原則4 |
| W-12 | 「はじめの診断を含む表示です」の注記は**維持**（誠実さは資産） |
| W-13 | 構成比に対する評価文（「バランスが良い/悪い」）を一切添えない |
| W-14 | 「充足度ポイント」は**廃止**。過去値も表示しない |

## 4. 週間レポートの扱い

### 4.1 現状の問題

現行は「週に2日以上記録するとレポートを作れます」でゲートされ、初回訪問では空です（C-07）。**原則4（空の状態を作らない）に違反しています。**

### 4.2 新仕様

| 項目 | 現行 | 新 |
|---|---|---|
| 名称 | 週間レポート | **今週のまとめ** |
| 生成条件 | 週2日以上の記録 | **点検が1回完了していれば生成**（0件選択でも生成） |
| 生成タイミング | ユーザーが「生成」ボタンを押す | **点検完了時に自動生成**（ボタンを押させない） |
| AIコメント | Pro のみ | Pro のみ（維持） |
| 未生成時の表示 | 「まだレポートがありません」 | **タブに出さない** |

### 4.3 「今週のまとめ」の内容

```
┌──────────────────────────────────────────┐
│  8/26 - 9/1 のまとめ                      │
│                                          │
│  支えになったもの                         │
│   木曜のバンド ●●●                        │
│   Aさん       ●●                          │
│   睡眠        ●                           │
│                                          │
│  この先の予定                             │
│   ◯◯の卒業配信 まで あと13日              │
│   → いま備えていること: Aさんと約束する    │
│                                          │
│  ── Pro ──                                │
│  今週のひとこと（AI）                      │
│  「木曜のバンドが3週続いています。卒業配信  │
│   のあと、この場所があるのは大きいかも      │
│   しれません。」                           │
└──────────────────────────────────────────┘
```

**AIコメントの制約**（→ `08` と共通）

| 禁止 | 理由 |
|---|---|
| 「◯◯は20%を占めており、週0.3回」のような機械的な数値引用 | 冷たい。競合レビュー最多の不満パターン（C-10, E-09） |
| 「ネガティブが多いですね」 | muute の失敗の再現（E-09） |
| 「〜すべきです」「〜しましょう」 | 宿題化 |
| 前週との比較で減少を指摘 | 判定（原則1） |

## 5. 育成提案の扱い

現行には「次に育てるといい柱」の提案と、設定画面に「育成提案を表示しない」トグルがあります。

### 5.1 判断: 独立機能としては廃止し、揺れイベントに紐づける

| 理由 |
|---|
| 「次に育てるといい柱」は**文脈のない宿題**であり、原則1に違反 |
| 「表示しない」トグルが存在すること自体が、**この機能が negative に受け取られている証拠** |
| 同じ提案を「〈卒業配信〉に備えて」という文脈に載せると、宿題ではなく**手段**になる |

### 5.2 移行

| 現行 | 新 |
|---|---|
| ホームの「次に育てるといい柱」 | **撤去** |
| 設定の「育成提案を表示しない」トグル | **撤去**（提案自体が文脈に紐づくため不要） |
| 提案のロジック | `05#5.3` の `PrepAction` 生成規則に統合 |

**唯一の例外**: 週次点検で確かな柱が0件の状態が4週続いた場合、点検完了後に**1回だけ**静かに提示します。

> 「もし気が向いたら、昔つながっていた人の名前をひとつ、登録しておくだけでもいいかもしれません。」

これも「〜しましょう」ではなく可能性の提示に留めます。

## 6. 移行 {#migration}

### 6.1 既存の日次記録データ

> 現行スキーマ未確認のため、以下は方針です（→ `00-current-state.md#3`）。

| 手順 | 内容 |
|---|---|
| 1 | 既存の日次レコードを `week_start` でグループ化 |
| 2 | 同一週・同一カテゴリの複数レコードを1つの `WeeklyCheckEntry` にマージ |
| 3 | `level` は「その週に何日出てきたか」を 1..3 にクランプ（1-2日→1、3-4日→2、5日以上→3） |
| 4 | 「充足度ポイント」は変換せず破棄 |
| 5 | カテゴリ → `Pillar` の変換は `02-domain-model.md#6` の規則に従う |
| 6 | 変換結果を検証する画面を**ユーザーに見せない**（勝手に変わったことを強調しない） |

### 6.2 ユーザーへの説明

**「毎日の記録がなくなった」は喪失として受け取られます。** 必ず事前に、理由とともに説明します。

> **記録を、週に1回にしました。**
>
> これまで毎日の記録をお願いしていましたが、週に1回に変えます。
>
> 毎日つけていただいたデータを見返して、そして世界中の研究を調べて、ひとつわかったことがあります。**毎日記録すること自体には、心を軽くする効果が確認されていません。**（気分の記録についての研究をまとめた2026年の論文では、記録だけでは症状の改善が確認できませんでした。）
>
> それよりも効くとわかっているのは、**支えになる人や居場所が増えること**です。そちらに時間を使ってもらえるように、アプリの側を軽くします。
>
> 毎日つけたい方は、これまで通りつけられます。ただ、**つけなくても大丈夫**になりました。

### 6.3 日次記録を続けたいユーザーへの配慮

- 週次点検は**週の途中でも何度でも編集できる**ため、実質的に日次でも運用可能
- ただし日次専用のUIは提供しない（二重の導線はプロダクトをぼやけさせる）
- 設定に「毎日リマインドしてほしい」オプションは**置かない**（原則5に反する）

## 7. エッジケース

| # | ケース | 挙動 |
|---|---|---|
| E-01 | 柱が0件の状態で点検を開く | 「まず、支えになっているものを1つ登録しませんか」→ 柱追加フロー（→ `07`）。**オンボで防ぐのが本筋** |
| E-02 | 週をまたいで点検画面を開いたまま送信 | 開いた時点の `week_start` に保存。ズレの警告は出さない |
| E-03 | タイムゾーンを変更した | `User.timezone` の変更後の週境界で計算。過去データは変換しない |
| E-04 | 2週以上空いた | 最新週の点検のみ可。「◯週分たまっています」と言わない（原則1） |
| E-05 | 柱をアーカイブした後の過去データ参照 | アーカイブ済み柱も過去のまとめには表示する（ラベルをスナップショット保持） |
| E-06 | 点検が0件保存で4週続く | §5.2 の1回だけの静かな提示。それ以上は何もしない |
| E-07 | `mood_note` にセーフティ検知 | 保存はする。保存完了画面に相談窓口カード（→ `03#2.3`） |

## 9. 計測

| 指標 | 定義 | 目標 |
|---|---|---|
| 週次点検 実施率 | アクティブユーザーのうち、その週に点検した割合 | **50%**（日次記録の実施率とは比較しない） |
| 4週連続実施率 | 4週続けて点検したユーザー | 30% |
| 平均選択数 | 1回の点検で選ばれた柱の数 | 観測（3〜5を想定） |
| 0件保存率 | 0件で完了した点検の割合 | 観測。**下げることを目標にしない** |
| `mood_note` 記入率 | 任意メモを書いた割合 | 観測（低くて正常） |
| 円グラフ到達率 | ふりかえりタブで折りたたみを開いた割合 | 観測。**10%を下回るなら機能を削除する判断材料** |
| 点検からの柱追加率 | 点検画面から柱を追加した割合 | 観測（`07` の入口として重要） |
