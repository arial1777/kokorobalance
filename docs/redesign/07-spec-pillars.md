# 07. 柱 仕様（再定義と承認）

**優先度: P2** / 対応課題: C-01, C-02, C-03, C-04

現行の「カテゴリ」を **3つの型を持つ「柱」** に再定義し、**承認（verification）** の概念を導入します。

---

## 1. なぜ変えるのか

### 1.1 看板の理論が、学術的に否定されている側にある

現行LPの「支えが3本あれば1本揺れても立っていられる」は、**self-complexity 緩衝仮説（Linville 1987）**そのものです。この理論の現状:

| 事実 | 出典 |
|---|---|
| 構成概念妥当性への疑義が1989年以降に提起され、**同様のデザインの複数の研究がストレス緩衝効果を再現できなかった** | E-01 |
| メタ分析（2002）: self-complexity は well-being と**負に、しかし弱く**相関。**ストレス緩衝仮説への支持はほとんど見出されなかった** | E-02 |
| 「低い自己複雑性の利点」を示す逆方向の研究も存在 | E-02 |

**「支えを分散すればストレスに強くなる」という一般化されたポートフォリオ理論は、学術的に支持されていません。** 金融のアナロジー（分散＝リスク低減）が感情・アイデンティティ領域で成立するという実証はありません。

### 1.2 しかし、隣に強い根拠がある

効いているのは「分散」ではなく「**主観的に重要で、他者から承認された社会的グループへの帰属**」という具体的なメカニズムです。

| 研究 | 内容 | 効果量 |
|---|---|---|
| 縦断コホート（n=5,055、2年追跡 / n=4,087、4年） | 既にうつのある人で、**グループを1つ増やすと再発リスク−24%、3つで−63%**。効果は非うつ者より**うつ者において強い** | E-03 |
| Groups 4 Health 非劣性RCT（15-25歳、n=174、12ヶ月追跡） | 抑うつ **d=−0.71**（CBT の d=−0.91 に非劣性）、孤独感 **d=−1.07**（CBT の −0.89 を上回る） | E-04 |
| Phase 2 RCT（n=120） | 「複数グループへの帰属感」自体が **d=0.52** で強化 | E-04 |

比較: 気分モニタリング介入は SMD **0.08〜0.25（有意でない）**（E-16）。**桁が違います。**

### 1.3 ただし、決定的な条件がある

identity accumulation 研究の知見:

> **アイデンティティ累積が well-being を高めるのは、それらのアイデンティティが高度に "verified"（他者から承認・確認されている）場合のみ。verify されていないアイデンティティの累積は well-being を低下させる。**（E-05）

**したがって「柱の本数を数えて増やせと促す」現行設計は、有害になりうる**ということです。

### 1.4 現行カテゴリの構造的問題

現行の24カテゴリのうち、**他者を伴うのは「人」グループの4項目のみ**（恋人/家族/友達/同僚）。残り20項目は単独活動です（睡眠・投資・筋トレ・読書・ゲーム・音楽・1人時間・貯金…）。

**エビデンスがある軸（社会的つながり）ではなく、ない軸（活動の種類）を分散させています。**

## 2. 柱の再定義

### 2.1 3つの型

| `kind` | UI表記 | 定義 | 例 | 承認 | 「柱」に数える |
|---|---|---|---|---|---|
| `place` | **居場所** | 継続的に所属し、他者から所属を認識されうる集団 | 職場のチーム、木曜のバンド、◯◯推し界、家族、常連の店、サークル、オンラインの鍵アカ仲間 | ○ | **○** |
| `relation` | **相手** | 特定個人との関係 | Aさん、妹、同僚のBさん、恋人 | ○ | **○** |
| `habit` | **習慣** | 単独で完結する活動 | 睡眠、朝の散歩、筋トレ、投資、読書、ゲーム | × | **×** |

### 2.2 「習慣」を柱から外す理由と、外し方

**理由**: 承認の対象になりえないため、§1.3 の条件を満たせません。「習慣が10個あるから支えが10本ある」とは言えません。

**外し方が重要です。** 「あなたの柱が減りました」と受け取られてはいけません。

| やること | やらないこと |
|---|---|
| 「習慣」という**別の名前を与えて肯定する** | 「柱ではありません」と否定する |
| 週次点検では**柱と並べて同じように選べる** | 習慣を選べなくする / 二軍扱いのUIにする |
| 支えリスト（`05#6.2`）にも**含める** | 当日の支えから除外する |
| 移行時に理由を説明する（`02-domain-model.md#6`） | 黙って数を減らす |

**習慣は価値がないのではなく、「本数」という指標に乗せられないだけ**という立場を明確にします。

### 2.3 「推し」の扱い（重要な設計判断）

現行では「推し」グループ（アイドル/アーティスト/VTuber）は単独活動として扱われています。**これを `place` になりうるものとして扱い直します。**

| ユーザーの状態 | `kind` | 理由 |
|---|---|---|
| ファンコミュニティ・同担・現場の知り合いがいる | **`place`** | 社会的帰属が成立している。承認の対象になる |
| ひとりで追っている | `habit` | 帰属ではない。ただし**価値を否定しない** |

**判定方法**: 柱の登録時に1問だけ聞きます。

```
◯◯推し界 について
  そのファンの人たちと、やりとりはありますか？
  [ ある ]  [ ひとりで追っている ]  [ こたえない ]
```

- `ある` → `place`
- `ひとりで追っている` / `こたえない` → `habit`
- **後から変更できる**（現場に行き始めたら `place` に上がる）

**メッセージの反転**: 現行LPは「推しの卒業発表を見た日」を脆さの象徴として描いていますが、20代女性の45%が推しを持ち、推し活支出は物価高でも54.0%が全く削らない（E-14）。**推し活はすでに機能しているセルフケアです。**

| 旧メッセージ | 新メッセージ |
|---|---|
| 「推しだけでは危ない」 | 「**卒業発表の日に備えておこう**」 |
| 「支えを分散させましょう」 | 「同じものを好きな人と、話せる場所はありますか？」 |

## 3. 承認（Verification）

### 3.1 状態

| 状態 | 条件 | UI表記 |
|---|---|---|
| **確かな柱** | `kind ∈ {place, relation}` かつ `verified_at IS NOT NULL` | 「確かな柱」 |
| **育て中** | `kind ∈ {place, relation}` かつ `verified_at IS NULL` | 「育て中」 |
| **習慣** | `kind = habit` | 「習慣」 |

### 3.2 承認の3経路

| `verification_source` | 条件 | 根拠 |
|---|---|---|
| `recurring_check` | **同一の柱が3週連続で週次点検に選ばれた** | 継続的な関与は帰属の代理指標 |
| `pair` | **ペアの相手が承認した**（→ `09`） | 最も強い承認。他者による確認そのもの |
| `self_declared` | ユーザーが「相手も、私がここにいると思っている」に明示的に答えた | 弱いが、主観的重要性は効果の前提でもある（E-04） |

### 3.3 `self_declared` の問い方

柱の登録時、または育て中の柱について、**1問だけ**聞きます。

```
木曜のバンド について
  そこにいる人たちも、あなたがそこにいると
  思っていそうですか？

  [ 思う ]  [ わからない ]  [ まだかな ]
```

- `思う` → `verified_at` を設定、`source = self_declared`
- `わからない` / `まだかな` → 育て中のまま
- **「まだかな」を選んだことをネガティブに扱わない**。次回は4週後まで聞かない

### 3.4 降格

| 条件 | 挙動 |
|---|---|
| 8週間、週次点検に一度も選ばれない | `verified_at` を null に戻す（育て中へ） |
| ペアが解消された（`source = pair` だった場合） | `recurring_check` の条件を満たすなら維持、満たさないなら育て中へ |

**降格を通知してはいけません。** 表示上、静かに移動するだけです（原則1）。「〈木曜のバンド〉が確かな柱から外れました」という通知は、最も残酷な通知です。

### 3.5 本数の表示規則

| ID | 要件 |
|---|---|
| P-01 | **主画面（「今週」タブ）に柱の本数を表示しない** |
| P-02 | ふりかえりタブでは「確かな柱 N / 育て中 M / 習慣 K」を**分けて**表示し、合計値を強調しない |
| P-03 | 「0本」を表示しない。0件の場合はセクション自体を出さない（原則4） |
| P-04 | 「3本以上が目標」等の目標値を表示しない |
| P-05 | 本数の増減を通知・アニメーションで祝わない/悼まない |

**「3本」という数字をプロダクト内の目標として提示しません。** LPのコピー（「1本より3本」）はブランドメッセージとして残せますが、アプリ内で達成すべき数値として扱いません。

## 4. 柱の登録

### 4.1 オンボーディング

原則4（空の状態を作らない）に基づき、**オンボ完了時に必ず2件以上の柱が存在する**状態を作ります。

```
オンボーディング（柱のパート）
  Step1: 「いま、あなたを支えているものは？」
          → 大分類から選ぶ（居場所 / 相手 / 習慣）
  Step2: 型ごとに具体を入れる
          居場所: 候補（職場・学校・サークル・推しのコミュニティ・お店・オンライン）から選び、
                  自分の言葉でラベルを付ける（例: 「木曜のバンド」）
          相手  : 「名前やあだ名でどうぞ。ここに書いた名前は誰にも見えません。」
          習慣  : 現行の候補リストを流用
  Step3: 重要度を3段階で（`importance`）
  Step4: 揺れやすい柱にフラグを立てる（任意）
          「これが揺れたらしんどい、と思うものはありますか？」
  → 最低2件登録するまで進めない（うち1件は place / relation を推奨するが強制しない）
```

**要件**

| ID | 要件 |
|---|---|
| P-10 | 柱のラベルは**ユーザーが自由に書ける**（20文字以内）。固定カテゴリ名を強制しない |
| P-11 | 相手の名前について「**誰にも見えません**」を明示（ペア機能でも共有しない → `09`） |
| P-12 | 最低2件の登録を完了条件とする。ただし**全て `habit` でも通す**（強制すると離脱する） |
| P-13 | 現行の8色選択と候補カテゴリは資産として流用する |
| P-14 | `label` 保存時にセーフティ判定を通す（→ `03`） |
| P-15 | 有効な柱は最大30件。超過時は「多すぎると見えなくなります」と伝える |

### 4.2 後からの追加

| 入口 | 位置 |
|---|---|
| 週次点検の画面内 | 「＋ 新しく追加する」（→ `06#2.4` W-04） |
| 備えの完了時 | 「新しい柱として登録しますか？」（例: 昔の友人に連絡した → その人を柱として登録） |
| 設定 > 柱の管理 | 現行のカテゴリ管理画面を流用 |
| ふりかえりタブ | 柱の一覧から追加 |

**「備えの完了時」が最重要の入口です。** 揺れ予報の備えを実行した結果として柱が増えるのが、このプロダクトの理想的なループです。

### 4.3 削除

- 論理削除（`archived_at`）。**物理削除しない**（過去のふりかえりと支えリストが参照する）
- 削除時に「本当に削除しますか」以外の引き止めをしない
- 削除した柱が過去のまとめに出てくることは説明する

## 5. 現行カテゴリからの移行

`02-domain-model.md#6` の規則を再掲・詳細化します。

| 現行グループ | 現行項目 | 新 `kind` | 移行時の扱い |
|---|---|---|---|
| 人 | 恋人 / 家族 / 友達 / 同僚 | `relation` | **「具体的に誰か」を聞き直す機会を1回作る。** スキップ可（そのままのラベルで残る） |
| 推し | アイドル / アーティスト / VTuber | `place` **または** `habit` | §2.3 の1問で判定 |
| 趣味 | ゲーム/音楽/映画/カフェ/読書/1人時間 | `habit` | ただし「カフェ」は `place` 候補として1問聞く（常連の店は居場所） |
| 自己成長 | 勉強/筋トレ/資格/副業 | `habit` | |
| 健康 | 運動/散歩/温泉/睡眠 | `habit` | Apple Health 連携で自動更新の候補（→ `04#6`） |
| 仕事 | 達成感/給料 | `habit` | **「職場のチーム」を `place` として別に登録する導線を1回提示** |
| お金 | 投資/貯金 | `habit` | |

### 移行時の一斉通知

`02-domain-model.md#6` の文面を使用。要点:

> 減ったわけではありません。**人や居場所とのつながりだけを「柱」と呼ぶことにしたのは、そこにいちばん確かな研究の裏付けがあるからです。**

さらに、移行後の初回起動時に**「居場所を1つ、登録してみませんか？」を1回だけ**提示します（強制しない）。

## 6. 訴求で使ってよい表現・いけない表現

マーケティング・アプリ内コピーの両方に適用します。

### 使ってよい

| 表現 | 根拠 |
|---|---|
| 「居場所を1つ増やすと、うつの再発リスクは24%下がる（5,055人・2年追跡）」 | E-03。**「既にうつのある人において」という条件を省略しない** |
| 「つながりを増やす取り組みは、認知行動療法と同じくらいの効果が確認されています」 | E-04（G4H の非劣性RCT） |
| 「支えは、数より、確かさ」 | E-05（verification 条件） |

### 使ってはいけない

| 表現 | 理由 |
|---|---|
| 「心のポートフォリオを分散させてリスクを下げる」 | 金融アナロジーは実証されていない（§1.1） |
| 「支えが多い人はストレスに強い」 | self-complexity 緩衝仮説。再現失敗（E-01, E-02） |
| 「3本の柱があれば大丈夫」 | 数の保証はできない。また verification 条件を無視している |
| 「あなたのバランススコアは◯点」 | 尺度の妥当性が確立されていない（ikigai・self-complexity・emodiversity すべて測定の妥当性が主要な批判点 — E-30） |
| 「感情の多様性が高いほど健康」 | emodiversity は統計的アーティファクト批判が未決着（E-31） |

> **注記**: 「あなたのポートフォリオスコア」型の指標を作ると、self-complexity / ikigai / emodiversity が受けたのと同じ「尺度の妥当性」批判を受けます。**独自スコアを作らないことが、この領域での正しい判断です。**

## 7. エッジケース

| # | ケース | 挙動 |
|---|---|---|
| E-01 | 柱が全て `habit` のユーザー | 「確かな柱」セクションを表示しない（0本と書かない）。当日画面は `05#6.5` の0件表示 |
| E-02 | `relation` の柱の相手と関係が終わった | ユーザーがアーカイブする。**アプリから「まだ支えですか？」と聞かない** |
| E-03 | 同じ実体を `place` と `relation` の両方で登録（バンドとバンドのAさん） | 許容する。重複チェックをしない |
| E-04 | 承認された柱が `is_fragile = true`（恋人など） | 矛盾ではない。確かな柱であり、かつ揺れやすい柱でありうる |
| E-05 | 3週連続で選ばれて承認 → 4週目に選ばれない | 即座に降格しない（8週ルール）。静かに維持 |
| E-06 | ペアで承認された柱を、ユーザー自身がアーカイブ | アーカイブを優先。ペアには通知しない |
| E-07 | `importance` を全て3にする | 許容。並び順は点検の `level` で決まるため実害なし |
| E-08 | 柱のラベルに他者の実名 | 許容するが、`P-11` で「誰にも見えません」を明示済み。ペアにも共有しない |

## 9. 計測

| 指標 | 定義 | 目標 |
|---|---|---|
| オンボ時の `place`/`relation` 登録率 | オンボで社会的な柱を1件以上登録した割合 | **60%** |
| 確かな柱への昇格率 | 育て中の柱が承認に至る割合（8週以内） | 40% |
| 経路別の承認内訳 | `recurring_check` / `pair` / `self_declared` の比率 | 観測 |
| 柱の新規追加率 | 月あたり柱が1件以上増えたユーザーの割合 | **20%**（プロダクトの目的そのもの） |
| 備え完了経由の柱追加 | `PrepAction` 完了時に柱を追加した割合 | 観測（理想的ループの指標） |
| 「推し」の `place` 判定率 | 推し系の柱のうち `place` になった割合 | 観測 |
| 降格率 | 8週ルールで育て中に戻った割合 | 観測。**高い場合は8週の閾値を見直す** |
