# 09. ペア 仕様（相互承認）

**優先度: P3** / 対応課題: C-03（承認の実装）

1人だけ招待できる、**相互承認のための1対1の関係**です。コミュニティではありません。

---

## 1. なぜ作るのか

### 1.1 ピアサポートが継続率の最上位

| 事実 | 出典 |
|---|---|
| メンタルヘルスアプリの**30日継続率**: ピアサポート **8.9%**（最上位）> トラッカー 6.1% > マインドフルネス 4.7% > 呼吸法 0.0% | E-17 |
| **open rate**（DAU）: ピアサポート **17.0%** > トラッカー 6.3% > 呼吸法 1.6% | E-17 |
| 臨床試験でも、**人間のフィードバックがある研究は脱落率が低い** | E-34 |
| VC の評価: 「**human in the loop はもはや機能ではなく前提条件（precondition, not a feature）**」 | E-35 |

### 1.2 verification 条件の実装でもある

`07-spec-pillars.md#1.3` の通り、**支えの累積が well-being を高めるのは、それが他者から承認されている場合のみ**です（E-05）。

現行アプリの承認は自己申告しかありえません。**ペアは「他者による承認」を唯一実装できる手段**です。

### 1.3 なぜコミュニティにしないのか

| 理由 |
|---|
| **運営コストとリスク**: モデレーションが必要。メンタルヘルス領域での失敗は致命的 |
| **2026年のトレンドと逆行**: Z世代は「SNS疲れ」「映えからリアルへ」「鍵アカ文化」。公開シェアは逆行（E-23） |
| **段階として正しい**: 1対1で効果が確認できてから拡張する。逆順にはできない |

## 2. 何を共有するのか（最重要）

**共有される情報を極小に絞ります。** ここを間違えると、プロダクトが「見せ合うSNS」になり、原則1（判定しない）が崩壊します。

### 2.1 共有する

| 情報 | 粒度 |
|---|---|
| 相手の表示名（`display_name`） | ユーザーが設定したもの。本名を要求しない |
| **今週、点検をしたかどうか** | したか / していないか の2値のみ |
| **確かな柱と育て中の柱の「色」だけ** | ラベル・種類・本数の内訳は共有しない |
| **揺れそうな日が近いこと** | 「◯◯さんは、9月15日に揺れそうな日があります」— **タイトルは共有しない**（ユーザーが明示的に共有を選んだ場合のみタイトルを出す） |
| **承認のやりとり** | 「この柱を確かな柱として承認してほしい」の依頼と承認 |

### 2.2 共有しない（絶対）

| 情報 | 理由 |
|---|---|
| 柱のラベル（「Aさん」「木曜のバンド」） | `07` P-11 で「誰にも見えません」と約束している |
| `mood_note` / `ShakeReview.note` | 自由記述は最も機微 |
| 壁打ちの会話 | 論外 |
| 円グラフ・構成比 | 比較を生む |
| 柱の本数 | 比較を生む（原則2） |
| 揺れイベントのタイトル（既定） | ユーザーが選んだ場合のみ |
| セーフティ検知の事実 | **絶対に共有しない**（→ `03#4.3`：通報・第三者連絡はしない） |

### 2.3 相手に見える画面

```
┌──────────────────────────────────────────┐
│  ペア                                     │
│                                          │
│  ┌────────────────────────────────────┐  │
│  │  みかん さん                         │  │
│  │                                     │  │
│  │  今週の点検 ── 済                    │  │
│  │  柱  ●●●○○                          │  │
│  │                                     │  │
│  │  9月15日に、揺れそうな日があります    │  │
│  │                                     │  │
│  │  ┌──────────────────────────────┐  │  │
│  │  │ 承認してほしい柱が1つあります  │  │  │
│  │  │                    [ 見る ]   │  │  │
│  │  └──────────────────────────────┘  │  │
│  └────────────────────────────────────┘  │
│                                          │
│  ▸ ペアを解消する                         │
└──────────────────────────────────────────┘
```

色の丸（`●●●○○`）は**確かな柱の色を3つまで**と、育て中を白丸で表現。**数を数えられる形にしないため、5個で固定**し、それ以上は表示しません。

## 3. 承認のフロー

### 3.1 依頼

ユーザーが育て中の柱について、ペアに承認を依頼します。

```
┌──────────────────────────────────────────┐
│  木曜のバンド                             │
│  育て中                                   │
│                                          │
│  みかん さんに、この柱を知ってもらいますか？│
│                                          │
│  相手に見えるのは、この名前だけです。      │
│  （「木曜のバンド」）                      │
│                                          │
│                     [ 送る ] [ やめる ]   │
└──────────────────────────────────────────┘
```

**重要**: 承認依頼のときだけ、**その柱のラベルが相手に見えます**。§2.2 の原則に対する例外なので、**送信前に明示的に警告します**（「相手に見えるのは、この名前だけです」）。

### 3.2 承認

相手側の画面:

```
┌──────────────────────────────────────────┐
│  みかん さんから                          │
│                                          │
│  「木曜のバンド」                         │
│  これが、みかんさんの支えになっていること   │
│  を知っていますか？                       │
│                                          │
│  [ 知っている ]  [ よく知らない ]          │
│                                          │
│  ※どちらを選んでも、相手には「見た」こと   │
│    だけが伝わります。                     │
└──────────────────────────────────────────┘
```

| 選択 | 挙動 |
|---|---|
| `知っている` | `verified_at` を設定、`verification_source = pair`。依頼者に `N-07` を送信 |
| `よく知らない` | **依頼者には「見た」ことだけが伝わる。** 「知らない」とは伝えない |

**「よく知らない」が伝わってはいけません。** 「あなたの支えを、相手は知らないと言っています」という通知は、このプロダクトが絶対に送ってはいけないメッセージです。

### 3.3 承認された側の通知

`N-07`: 「みかんさんが、あなたの〈木曜のバンド〉を知っていると答えました。**確かな柱になりました。**」

**祝いすぎないこと。** 静かな一文で十分です。

## 4. ペアの成立と解消

### 4.1 招待

| 手段 | 仕様 |
|---|---|
| 招待コード | 6〜8文字の英数。**有効期限7日**。1回使用で失効 |
| 共有方法 | OSの共有シート（LINE・メール等、ユーザーの任意）。**アプリからSNS投稿しない** |
| 受諾 | コード入力 または ディープリンク |

**アプリ内でユーザーを検索する機能を実装しません。** 招待コードを知っている人だけがつながれます（メンタルヘルス領域で発見可能性を持たせるリスクを避ける）。

### 4.2 制約

| ID | 要件 |
|---|---|
| PR-01 | 1ユーザーが同時に持てる `active` なペアは**1つだけ** |
| PR-02 | 招待は同時に1件のみ発行できる（乱発を防ぐ） |
| PR-03 | ペア成立時に、**両者に同じ説明を出す**（何が共有され、何が共有されないか） |
| PR-04 | **どちらからでも、いつでも、理由なく解消できる** |
| PR-05 | 解消は相手に通知される（黙って消えるのは不安を生む）。ただし**理由は伝えない** |
| PR-06 | 解消後、共有されていた情報は即座に見えなくなる |
| PR-07 | `verification_source = pair` の柱は、`07#3.4` の規則で処理（他の承認条件を満たすなら維持） |
| PR-08 | 一時停止（`paused`）を提供する（解消せずに共有を止めたいニーズ） |
| PR-09 | 同じ相手との再ペアは可能。ただし解消後**7日間はクールダウン**（衝動的な再接続を防ぐ） |

### 4.3 未成年・安全性

| リスク | 対策 |
|---|---|
| グルーミング・見知らぬ他人との接続 | ユーザー検索を実装しない（§4.1）。招待は既知の相手に限られる |
| 相手からの圧力（「点検してないよ」等） | **メッセージ機能を実装しない**（§5） |
| 相手のセーフティ状況を知りたいニーズ | **応じない**（§2.2）。危機の共有は本人の意思のみ |

## 5. 実装しない機能

「ペア」を拡張したくなる誘惑が強い領域なので、**明示的に禁止します**。

| 実装しない | 理由 |
|---|---|
| **メッセージ・チャット機能** | モデレーション不能。かつ圧力の経路になる。連絡は既存のLINE等で足りる |
| リアクション・スタンプ | 「反応がない」ことが傷になる |
| 相手の点検を促す機能（リマインド送信） | 相互監視。原則1に違反 |
| ランキング・比較 | 原則2に違反 |
| 3人以上のグループ | §1.3。段階を飛ばさない |
| ペアの相手の柱の中身を見る | §2.2 |
| 「ペアがいる人は継続率が高い」等の訴求で招待を強く促す | 誘導が強いと関係を消費させる |

## 6. エッジケース

| # | ケース | 挙動 |
|---|---|---|
| E-01 | 招待コードが期限切れ | 「このコードは使えなくなっています」。再発行を促す |
| E-02 | 招待した相手が既に別のペアを持っている | 「相手はすでに別の方とペアになっています」（相手が誰かは伝えない） |
| E-03 | 承認依頼をしたが相手が7日以上反応しない | 静かに依頼を取り下げる。**依頼者に「無視されました」と伝えない** |
| E-04 | ペアの相手が退会 | ペアを `ended` に。「ペアが解消されました」のみ通知（退会の事実は伝えない） |
| E-05 | 承認済みの柱をペア解消後に扱う | `07#3.4` に従う。**降格する場合も通知しない** |
| E-06 | 相手のセーフティ検知が発火 | **何も共有しない。** ペア画面に変化を出さない |
| E-07 | 承認依頼の柱ラベルにセーフティ検知語 | `03` の判定を通す。`block` なら依頼を送らず、依頼者に窓口カードを出す |
| E-08 | ペアの相手が長期に不在（8週以上点検なし） | 「今週の点検 ── まだ」の表示のまま。**催促の導線を出さない** |
| E-09 | 揺れイベントのタイトル共有を後から取り消したい | いつでも取り消せる。取り消したことは相手に通知しない |

## 7. 受入基準

| # | 基準 |
|---|---|
| PR-A-01 | 招待コードで1対1のペアが成立する |
| PR-A-02 | アプリ内にユーザー検索機能が存在しない |
| PR-A-03 | ペア画面に相手の柱のラベル・本数・構成比・メモ・壁打ち内容が表示されない |
| PR-A-04 | 承認依頼時に「相手に見えるのはこの名前だけです」の警告が出る |
| PR-A-05 | `よく知らない` を選んだ結果が、依頼者に「知らない」として伝わらない |
| PR-A-06 | メッセージ・スタンプ・リマインド送信の機能が存在しない |
| PR-A-07 | どちらからでも1タップ（＋確認1回）でペアを解消できる |
| PR-A-08 | 解消後、共有情報が即座に見えなくなる |
| PR-A-09 | セーフティ検知の事実がペアに一切共有されない |
| PR-A-10 | ペア成立時に、共有される情報・されない情報の説明が両者に表示される |
| PR-A-11 | 相手の点検未実施に対する催促導線が存在しない |
| PR-A-12 | 柱の色表示が5個で固定され、本数を数えられない |

## 8. 計測

| 指標 | 定義 | 目標 |
|---|---|---|
| ペア成立率 | 全ユーザーのうち `active` なペアを持つ割合 | **15%**（高い目標を置かない。全員に必要な機能ではない） |
| 招待→受諾率 | 発行された招待のうち受諾された割合 | 40% |
| **ペア有無での30日継続率の差** | ペアあり群 vs なし群 | **ペアあり群が1.5倍以上**（E-17 のピアサポート優位が再現されるかの検証） |
| 承認依頼率 | ペアを持つユーザーのうち承認依頼をした割合 | 50% |
| 承認率 | 依頼に対する `知っている` の割合 | 観測 |
| ペア解消率 | 成立から90日以内の解消 | 観測。**30%超なら共有情報が多すぎる可能性** |
| 解消理由 | 任意アンケート（1問、スキップ可） | 観測 |

**検証の本質**: この機能の価値は「ペアあり群の継続率が有意に高いか」の1点です。差が出なければ、`03`〜`08` に工数を戻してください。**ピアサポートが効くというエビデンスは他社アプリのものであり、この実装で再現される保証はありません。**
