# 11. 計測設計

各仕様書の末尾にある指標を統合し、**何を見て、何を見ないか**を定義します。

---

## 1. 計測の原則

### 1.1 見てはいけない指標

このプロダクトでは、以下を**主要指標として追ってはいけません**。原則1・2（`01-concept.md#3`）と矛盾するためです。

| 追わない指標 | 理由 |
|---|---|
| **記録日数 / 連続記録日数** | 原則2。上げようとすると催促通知が生まれ、punishy 設計に戻る |
| DAU（日次アクティブ） | 原則5（毎日を要求しない）と矛盾。**WAU を見る** |
| セッション時間 | 長い＝良いではない。30秒で終わるのが正しい |
| 壁打ちの利用回数 | 依存の形成を意味する可能性がある（→ `08#9`） |
| **セーフティ `block` の発火率（下げる方向）** | 検知を弱めるインセンティブが生まれる（→ `03#9`） |
| 通知の開封率（上げる方向） | 通知を増やす／煽る方向のインセンティブ |

### 1.2 指標の階層

```
北極星
  └── 揺れイベントを「支えられて越えた」率
        │
        ├── 先行指標: イベント登録率 → 備え完了率 → 当日到達率 → ふりかえり実施率
        │
        ├── リテンション: 30日 / 90日継続率、WAU/MAU
        │
        ├── プロダクトの目的: 柱の新規追加率、確かな柱への昇格率
        │
        ├── 収益: 年額比率、初回更新率
        │
        └── ガードレール: セーフティ偽陰性、「的外れ」報告率、返金率
```

## 2. 北極星指標

> **揺れイベントのふりかえりで `was_supported ∈ {yes, partly}` と回答した率**

| 項目 | 値 |
|---|---|
| 定義 | `count(ShakeReview where was_supported in ('yes','partly')) / count(ShakeReview)` |
| 目標 | **60%** |
| 測定粒度 | 月次、`ShakeEvent.category` 別、`expected_shake` 別 |
| なぜこれか | プロダクトの約束そのもの。「記録した」ではなく「支えられた」を測る |
| **限界（正直に）** | 自己報告であり、ふりかえりを実施した人のバイアスがかかる。母数（ふりかえり実施率）と併せて必ず見ること |

### 補助指標: `felt_shake` と `expected_shake` の差

「備えたことで揺れが小さく感じられたか」の代理指標です。ただし**単独で解釈しないこと**（予測の精度が上がっただけの可能性がある）。

## 3. ファネル

### 3.1 オンボーディング

| # | ステップ | 目標通過率 |
|---|---|---|
| 1 | サインアップ完了 | — |
| 2 | 柱を2件以上登録（→ `07#4.1`） | 85% |
| 3 | うち `place`/`relation` を1件以上 | 60% |
| 4 | **揺れイベントを1件登録**（→ `05#4.4`） | **70%** |
| 5 | 通知許可（→ `04#4.3`） | **40%** |
| 6 | オンボ完了 | 80% |

**#4 が 40% を下回る場合、コンセプトのリスク1（言語化の認知負荷）が現実化しています**（→ `01-concept.md#12`）。

### 3.2 揺れ予報

| # | ステップ | 目標 |
|---|---|---|
| 1 | イベント登録 | — |
| 2 | 備えを `accepted` | 50% |
| 3 | 備えを `done` | **40%**（1に対して） |
| 4 | 当日に支えリストを開いた | 60% |
| 5 | ふりかえり実施 | 50% |
| 6 | **`was_supported ∈ {yes,partly}`** | **60%**（5に対して） |
| 7 | **2件目のイベントを登録** | **50%**（5に対して） |

**#7 がリピートの本質指標です。** 1回使って終わりなら、このプロダクトは成立しません。

## 4. リテンション

### 4.1 目標

| 指標 | 業界水準 | 目標 |
|---|---|---|
| **30日継続率** | 中央値 **3.3%** / トラッカー型 6.1% / ピアサポート型 8.9%（E-17） | **12%** |
| 90日継続率 | — | 7% |
| WAU / MAU | — | 45%（週次プロダクトとして） |
| 週次点検 実施率 | — | 50%（→ `06#9`） |

### 4.2 定義の注意

- 「継続」の定義を**アプリを開いたこと**にする（記録したことにしない。原則2）
- 30日継続率は**インストール日コホート**で測る（業界データと比較可能にするため）
- **業界データ（E-17）は Google Play のパネルデータであり、測定手法が異なります。** 厳密な比較はできない点を報告時に明記すること

### 4.3 セグメント別に必ず分けて見る

| セグメント | 見る理由 |
|---|---|
| 揺れイベント登録あり / なし | **コンセプトが効いているかの最重要検証** |
| ペアあり / なし | ピアサポート優位（E-17）が再現されるか（→ `09#8`） |
| `place`/`relation` の柱あり / `habit` のみ | 柱の再定義（`07`）が効いているか |
| 通知許可 / 拒否 | 配信基盤（`04`）の効果 |
| Free / Pro | |
| 流入元（ASOキーワード別） | `04#5.2` のキーワード戦略の検証 |

## 5. プロダクトの目的に対する指標

「継続」は手段であり、目的ではありません。**支えが実際に増えたか**を測ります。

| 指標 | 定義 | 目標 |
|---|---|---|
| **柱の新規追加率** | 月に1件以上、柱が増えたユーザーの割合 | **20%** |
| **`place`/`relation` の追加率** | 上記のうち社会的な柱だったもの | 60% |
| 確かな柱への昇格率 | 育て中の柱が8週以内に承認された割合 | 40% |
| **備え完了 → 柱追加** | `PrepAction` 完了時に柱を追加した割合 | 観測（**理想的ループの指標**） |
| 承認経路の内訳 | `recurring_check` / `pair` / `self_declared` | 観測 |

## 6. ガードレール指標

**悪化したらリリースを止める指標です。** 成長指標より上位に置きます。

| 指標 | 閾値 | アクション |
|---|---|---|
| **セーフティ偽陰性件数**（抽出レビュー） | **1件でも** | 辞書を即日更新。原因分析（→ `03#6`） |
| 「この返信は的外れ／つらかった」報告率 | 3%超 | 壁打ちのプロンプト・型選択を見直す（→ `08#9`） |
| 通知OFF率 | 20%超 | 通知の本数・文面を見直す（→ `04#4`） |
| アンインストール率（7日以内） | 業界比で悪化 | オンボの負荷を見直す |
| ストアレビュー平均 | 4.0未満 | 全レビューを読み、上位3つの不満に対応 |
| 返金・チャージバック率 | 1%超 | 課金訴求のダークパターンを疑う（→ `10#2.4`） |
| **揺れイベント当日の離脱**（支えリストを開いてすぐ閉じた率） | 50%超 | 支えリストの内容が空虚な可能性。§6.5 の0件表示を含めて検証 |

## 7. 定性の計測

数値だけでは足りない領域なので、**定性を運用に組み込みます**。

| 手段 | 内容 | 頻度 |
|---|---|---|
| **ストアレビューの全読** | iOS / Android の全レビューを読み、不満をタグ付けして集計 | 週次 |
| 「的外れ」報告の全読 | `08` の報告ボタン経由。全件レビュー | 週次 |
| 解約時アンケート | 1問のみ、スキップ可。選択式＋任意記述 | 常時 |
| ユーザーインタビュー | 揺れイベントを2件以上完了したユーザーに5名/月 | 月次 |
| **セーフティの抽出レビュー** | → `03#6.2`。資格保持者への月1回委託を推奨 | 月次 |

> **競合分析から得た教訓**: Awarefy・muute・Upmind の致命的な不満（オウム返し、ネガティブ否定、課金前の情報不足、ダークパターン）は**すべてストアレビューに書かれています**（E-09）。競合はこれを読んでいないか、読んで直していません。**週次でレビューを全読することが、最もコストの低い競争優位です。**

## 8. 実験計画

### 8.1 検証すべき仮説（優先順）

| # | 仮説 | 検証方法 | 判断 |
|---|---|---|---|
| **H1** | 揺れ予報があると継続率が上がる | イベント登録あり/なしのコホート比較（RCTではなく観察） | 30日継続率で**2倍以上**の差 |
| **H2** | 週次化しても実施率は日次より落ちない（むしろ上がる） | 移行前後の比較 + 段階リリース | 週次実施率50%以上 |
| **H3** | 柱を「人・居場所」に寄せると継続率が上がる | `place`/`relation` あり/なしの比較 | 有意な差 |
| **H4** | ペアがあると継続率が上がる | ペアあり/なしの比較 | **1.5倍以上**（→ `09#8`） |
| **H5** | 壁打ちを「毎日1往復」にすると Free の利用率が上がる | 変更前後の比較 | 週1回以上利用が40% |
| **H6** | 年額主導線で初回更新率が上がる | 年額/月額の380日継続比較 | 年額25%以上 |

### 8.2 A/Bテストの制約

**メンタルヘルス領域でのA/Bテストには倫理的制約があります。**

| 禁止 | 理由 |
|---|---|
| セーフティ機能のA/B（片方に検知を入れない） | 論外 |
| 相談窓口の表示有無のA/B | 同上 |
| 罪悪感・不安を煽るコピーのA/B | 短期の数値は上がる可能性があるが、原則1に違反 |
| 通知頻度を大幅に上げる群を作る | 実害が出る |

**許容される範囲**: コピーの文言（同等の温度のもの同士）、UIの配置、テンプレの見せ方、価格の提示順。

### 8.3 段階リリース

`06`（週次化）は既存ユーザーの体験を大きく変えるため、段階的に出します。

| 段階 | 対象 | 期間 |
|---|---|---|
| 1 | 新規ユーザーのみ | 4週 |
| 2 | 既存の非アクティブユーザー（30日以上未訪問） | 2週 |
| 3 | 既存アクティブユーザー（`06#6.2` の説明を先に配信） | — |

段階1で週次実施率が30%を下回った場合、段階2に進まず設計を見直します。

## 10. 実装上の要件

| ID | 要件 |
|---|---|
| ME-01 | イベント計測に**自由記述の本文を含めない**（`mood_note`、`note`、壁打ちの本文） |
| ME-02 | 柱のラベルを分析基盤に送らない（`kind` と ID のみ） |
| ME-03 | セーフティ関連のイベントは、他の分析イベントと**別経路**で送る（第三者の分析SDKに乗せない） |
| ME-04 | 第三者の分析・広告SDKに送るデータを最小限にし、プライバシーポリシーに列挙する |
| ME-05 | ユーザーが分析へのオプトアウトを選べる（セーフティの検知自体はオプトアウト不可 → `03#6.3`） |
| ME-06 | 30日継続率の算出方法をドキュメント化し、変更時は履歴を残す（過去との比較を壊さない） |
| ME-07 | 全指標に「観測のみ / 目標あり」のラベルを付け、**目標のない指標を最適化対象にしない** |
